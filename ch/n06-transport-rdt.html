Transport layer and reliable data transfer

Lectures 5–6 move down to the transport layer: how one host serves many processes (multiplexing), what UDP adds on top of IP (almost nothing, on purpose), how its checksum works, and then the central question of the course: how to build a reliable channel on top of an unreliable one. We build the protocol step by step, rdt 1.0 to rdt 3.0, measure why stop-and-wait is too slow, and fix it with pipelining: Go-Back-N and Selective Repeat.

1Transport services and protocols

The transport layer provides logical communication between application processes running on different hosts. It runs only in end systems: the sender breaks application messages into segments and passes them to the network layer; the receiver reassembles segments into messages and passes them up. The network layer, by contrast, provides logical communication between hosts.

Why

The lecture's analogy: a house with 12 kids sends letters to a house with 12 kids. Hosts = houses, processes = kids, application messages = letters in envelopes, network-layer protocol = the postal service, transport protocol = Ann and Bill, who collect the letters from the kids in their house and distribute the ones that arrive (multiplexing and demultiplexing). Ann and Bill only work inside the houses; they cannot speed up the mail truck.

Sender actions: get the message from the application, determine the header field values, create the segment, pass it to IP. Receiver actions: get the segment from IP, check the header values, extract the application message, demultiplex it up to the application via the socket.

2Multiplexing and demultiplexing

Multiplexing at the sender: gather data from several sockets and add a transport header (later used for demultiplexing). Demultiplexing at the receiver: use the header information to deliver each received segment to the correct socket. The host receives IP datagrams; each carries a source and destination IP address and one transport segment with a source and destination port.

Connectionless (UDP)

A UDP socket is identified by the 2-tuple (dest IP, dest port). All datagrams with the same destination port go to the same socket, even if they come from different source IPs or ports. The source port is the "return address" the server uses to reply.

Example from the lecture: A (port 9157) and C both send to B port 6428 → one socket on B. B no longer knows "who is who" from the socket alone.

Connection-oriented (TCP)

A TCP socket is identified by the 4-tuple (src IP, src port, dest IP, dest port). The receiver uses all four values to direct the segment. A server supports many simultaneous TCP sockets, one per connected client, all on the same server port.

Example: three clients connect to a web server on port 80 → three different sockets. If even one of the four values differs, it is a different socket. Non-persistent HTTP opens a new socket for every request.

3UDP: User Datagram Protocol (RFC 768)

UDP is a "no frills, bare bones" protocol: segments may be lost or delivered out of order, and there is no handshake and no per-connection state. Why use it? No connection setup (no RTT delay), simple (no state at sender or receiver), small header (8 bytes), and no congestion control, so it can blast away as fast as desired. Reliability, if needed, is added in the application layer.

Users: streaming multimedia (loss-tolerant, rate-sensitive), DNS, SNMP, HTTP/3 (QUIC adds reliability and congestion control on top of UDP).

4The Internet checksum

Goal: detect errors (flipped bits) in the transmitted segment. The sender treats the segment contents (header, data, and a pseudo-header with the IP addresses) as a sequence of 16-bit integers, adds them in one's complement arithmetic, and puts the complement of the sum in the checksum field. The receiver adds all the 16-bit words including the checksum: the result must be all 1s (0xFFFF). If not, an error is detected.

Adding two 16-bit words

Given

  • word 1 = 1110 0110 0110 0110, word 2 = 1101 0101 0101 0101

Solution

  1. Binary sum: 1 1011 1011 1011 1011 (17 bits: a carry out of the top bit)
  2. Wraparound: add the carry back into the lowest bit: 1011 1011 1011 1011 + 1 = 1011 1011 1011 1100
  3. Checksum = one's complement (flip every bit): 0100 0100 0100 0011
  4. Receiver: sum + checksum = 1011 1011 1011 1100 + 0100 0100 0100 0011 = 1111 1111 1111 1111 ✓
Exam trap

The checksum only detects; it never corrects. And it is weak: if one word gains +1 in some bit and another loses it in the same position (two bit flips that cancel), the sum is unchanged and the error goes undetected. Why have it in UDP at all if the link layer has a CRC? The end-to-end principle: not every link checks errors, and bits can be corrupted inside a router's memory.

5Building reliable data transfer: rdt 1.0 to 3.0

The interfaces: the application calls rdt_send(data); the sender side calls udt_send(pkt) to push a packet over the unreliable channel; on arrival rdt_rcv(pkt) is called; the receiver calls deliver_data(data) to hand data up. We describe sender and receiver with finite state machines (FSMs): event / actions on each transition. The complexity of the protocol depends entirely on what the channel can do wrong.

6Why stop-and-wait is too slow

Utilization Usender is the fraction of time the sender is busy sending. With stop-and-wait the sender transmits one packet (L/R), then idles a whole RTT waiting for the ACK:

U_sender = (L/R) / (RTT + L/R)

1 Gbps link, 15 ms propagation

Given

  • R = 1 Gbps, one-way propagation 15 ms → RTT = 30 ms, packet L = 8,000 bits (1 KB)

Solution

  1. dtrans = L/R = 8,000 / 109 = 8 μs
  2. U = 0.008 ms / 30.008 ms = 0.00027
  3. Throughput = L / (RTT + L/R) = 8,000 bits / 30.008 ms ≈ 267 kbps on a 1 Gbps link!
  4. The protocol, not the link, limits performance.

Pipelining: the sender allows multiple "in-flight", yet-to-be-acknowledged packets. With N packets per RTT: U = N·(L/R) / (RTT + L/R) (as long as that is ≤ 1). With N = 3 above, U = 0.00081, three times better. To fill the pipe completely, N·L must be about R·RTT (the bandwidth-delay product). Pipelining needs a range of sequence numbers (not just 0/1) and buffering at the sender and/or receiver. Two generic forms: Go-Back-N and Selective Repeat.

7Go-Back-N (GBN)

  • Sender: a window of up to N consecutive transmitted but unACKed packets, with a k-bit seq # in the header. Pointers: send_base (oldest unACKed) and nextseqnum (next to send).
  • Cumulative ACK: ACK(n) acknowledges all packets up to and including seq # n. On receiving ACK(n), move the window forward to begin at n+1.
  • One timer for the oldest in-flight packet. On timeout(n): retransmit packet n and all higher-seq packets in the window ("go back N").
  • Receiver: ACK-only. Always send an ACK for the correctly-received packet with the highest in-order seq #; this may produce duplicate ACKs. It needs to remember only rcv_base (expected seq #).
  • On an out-of-order packet: discard it (no receiver buffering) and re-ACK the highest in-order seq #.

GBN with N = 4, pkt2 lost

Given

  • The sender sends pkt0–pkt3 (window full).

Solution

  1. Receiver gets 0 → ack0, 1 → ack1; pkt2 is lost; gets 3 → out of order: discard, send ack1 again.
  2. ack0 and ack1 slide the window: the sender sends pkt4 and pkt5. The receiver discards both and sends ack1, ack1.
  3. pkt2 times out → the sender retransmits pkt2, pkt3, pkt4, pkt5.
  4. The receiver now accepts 2, 3, 4, 5 in order and ACKs each.
Remember

Window size limit for GBN with k-bit sequence numbers: N ≤ 2k − 1. With N = 2k, if all ACKs of a full window are lost, the receiver cannot tell a retransmitted old window from a new one.

8Selective Repeat (SR)

  • The receiver individually acknowledges every correctly received packet, and buffers out-of-order packets for eventual in-order delivery to the upper layer.
  • The sender keeps a timer for each unACKed packet; on timeout it retransmits only that packet.
  • Sender window: N consecutive seq #s. An ACK(n) inside the window marks n received; if n is the smallest unACKed, the window advances to the next unACKed seq #.
  • Receiver: pkt n in [rcv_base, rcv_base+N−1] → send ACK(n); if out of order, buffer; if in order, deliver it and all buffered in-order packets, and advance the window. pkt n in [rcv_base−N, rcv_base−1] (already delivered) → still send ACK(n), because the sender may not have got the earlier ACK. Otherwise ignore.

SR with N = 4, pkt2 lost

Given

  • Sender sends pkt0–pkt3.

Solution

  1. Receiver: 0 → deliver, ack0; 1 → deliver, ack1; 3 → buffer, ack3.
  2. Sender: ack0, ack1 slide the window → send pkt4, pkt5. ack3 is recorded (window can't pass 2 yet).
  3. Receiver buffers 4 and 5 and ACKs them.
  4. pkt2 times out → resend only pkt2. Receiver delivers 2, 3, 4, 5 at once and sends ack2.
Exam trap

The SR dilemma: seq #s 0, 1, 2, 3 (k = 2) and window N = 3. Case A: the sender sends 0, 1, 2, all ACKs are lost, it retransmits pkt0. Case B: all ACKs arrive, the sender sends 3, 0 (new), and pkt3 is lost. In both cases the receiver, whose window is now 3, 0, 1, sees a "pkt0" and accepts it as new data. In case A that is an old duplicate → wrong data delivered. Rule: N ≤ 2k−1 (window at most half the sequence space).

10Review

Two clients send UDP datagrams to the same server port. How many server sockets?

One. For TCP it would be two connection sockets (different 4-tuples).

What problem does each of rdt 2.0, 2.1 and 3.0 solve?

2.0: bit errors (checksum + ACK/NAK + retransmit). 2.1: corrupted ACK/NAK (1-bit sequence numbers to detect duplicates). 3.0: loss (timeout and retransmit).

Utilization of stop-and-wait with L/R = 1 ms and RTT = 9 ms?

1 / (9 + 1) = 0.1.

Seq numbers have 3 bits. Max window for GBN and for SR?

GBN: 23 − 1 = 7. SR: 22 = 4.

Why does an SR receiver re-ACK packets below its window?

The earlier ACK may have been lost; without a new ACK the sender's window would never move.
