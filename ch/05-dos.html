DoS and DDoS

Attacks on availability: from single-packet bugs (Ping of Death, Teardrop, LAND), through SYN floods and SYN cookies, application floods (HTTP flood, Slowloris), amplification (NTP, DNS), BGP route hijacking, up to advanced attacks on shared links and on TCP itself (Shrew, Coremelt, Crossfire).

1What denial of service is

A deliberate attempt to stop legitimate users from using a service: flooding the network, cutting a connection between two machines, blocking one person from a service, or disrupting a service for a specific system.

Not every outage is DoS. And DoS can be part of a bigger attack: in DHCP poisoning (chapter 04) the real server is knocked out so the rogue one answers first. Illegitimate use of resources (an anonymous FTP server filled with pirated software) also causes DoS.

Consuming scarce resources

Bandwidth, memory and disk, CPU, connections, the process table. The most common type.

Destroying or altering configuration

Changing the Windows registry, changing a router's routing tables.

Physical destruction

Unauthorized access to comms rooms, cables, power and cooling. Physical security.

The key word of the chapter: asymmetry

A good DoS costs the attacker little and the victim a lot. One SYN = 40 bytes for the attacker, a thread and a data structure on the server. A 60-byte DNS query = a 3,000-byte answer to the victim. Every defense in this chapter tries to restore the symmetry.

3One packet that crashes a system: Ping of Death, Teardrop, Bonk, LAND

Reminder: IP is connectionless and best effort; a large packet is split into fragments with the Identification, Flags and Fragment Offset fields, and the destination reassembles it (chapter 00 has the full algorithm). Every attack here abuses reassembly code that did not check edge cases.

Ping of Death

Max IP = 65,535 bytes. Max ICMP Echo data = 65,535 − 20 (IP) − 8 (ICMP) = 65,507. But fragments can "add up" to more: last fragment offset 8189 × 8 = 65,512 plus 100 bytes. Illegal, so nobody handled it: buffer overflow, freeze, crash, reboot.
Fix: patched OS, ICMP filtering.

Teardrop

Overlapping fragment offsets. A bad TCP/IP implementation crashes while reassembling (negative copy length).

Bonk

A huge offset. The same kind of crash.
Fix for both: a current TCP/IP stack.

LAND

A SYN where source = destination (IP and port). The system sends SYN/ACK to itself and loops until timeout. Windows XP SP2 locked the CPU.
Fix: ingress filtering (a packet from outside with an inside address is forged).

Real world

These attacks have been dead for a decade, but the pattern lives: CVE-2020-16898 ("Bad Neighbor", one ICMPv6 packet crashes Windows) and CVE-2024-38063 (IPv6 in Windows) are modern Pings of Death.

4Smurf, reverse path filtering and the echo loop

Smurf (chapter 03 and the animation): Echo Request to a broadcast address with the victim as source; the whole network answers the victim. Fixes: drop external packets to broadcast addresses, and reverse path filtering.

Reverse path filtering (Linux)

A packet with source X arrived on interface I. The kernel asks: "if I sent a reply to X, which interface would it leave from?" If not I, the packet is probably forged and dropped. Linux: net.ipv4.conf.all.rp_filter=1.

This is "your own resources against you" (UDP packet storm). Any service that answers every request works. Easy fix: disable or block those services.

5SYN flood

Why it works

For every SYN the server allocates state (a TCB, sometimes a thread) and waits for the ACK until timeout. There is a fixed limit of half-open connections. Sending a SYN costs the initiator nothing, but the responder must allocate resources: asymmetry. So a server on a fast network can be knocked out from a dial-up line.

With a 3-minute timeout, 128 SYNs every 3 minutes are enough to disable FreeBSD (Phrack 48, 1996). That is a low-rate SYN flood.

Events from the lecture

MS Blaster (2003): every infected machine sent 50 SYN/s to port 80 of windowsupdate.com. BetCris.com (2003): 20,000 bots = 2 Gb/s of SYN. Random source IPs, so attack SYNs look exactly like real ones. Estonia (2007): 115 ICMP floods and 4 SYN floods, 12 attacks of 70–95 Mb/s lasting 10+ hours. All traffic came from outside Estonia, so local ISPs blocked all foreign traffic until it ended, and damage inside the country was small.

Detection

SYN–FIN pairs

Normally every SYN has a FIN. RST breaks this: passive RST (closed port) and active RST (client aborts) are normal; assume ~75% active. Weakness: the attacker sends extra FIN/RST with other IPs/ports to "balance" the count, at the cost of half its bandwidth.

SYN – SYN/ACK pairs

Hard for the attacker to evade. But you must watch both inbound and outbound, and it only triggers when you are already flooded.

Prevention

Ingress filtering (RFC 2827 / BCP 38)

The edge router of 204.69.207.0/24 drops any outgoing packet with another source. Possible at the edges, hard in the core. Prevents spoofing at the source, but only if everyone does it.

uRPF (unicast reverse path forwarding)

Accept a packet on an interface only if the routing table places its source behind that interface (Cisco: ip verify unicast reverse-path). Needs symmetric routing; with asymmetric routing it drops legitimate packets.

Random deletion

When the queue is full, delete a random entry. Real connections complete in time; spoofed ones eventually get deleted. Easy to implement.

Proxy (Prolexic / Verisign)

A cloud proxy receives all SYNs, completes the handshake itself, and forwards only completed (ACKed) connections to the site.

6SYN cookies (Bernstein & Schenk)

The idea: the server keeps no state until the client proves it is real by sending a second message. All the state is encoded in the sequence number of the SYN/ACK; when an ACK returns with cookie+1, recompute and compare.

Verification: subtract 1 from the ACK number, check t has not expired, recompute s, and decode the MSS from the 3 bits to rebuild the connection entry.

Questions from the slide: why?

Why must the cookie be tamper-proof? Otherwise an attacker could compute a valid cookie without receiving the SYN/ACK, send a forged ACK and open connections from spoofed addresses. Hence a secret only the server knows.
Why must the client not be able to invert it? So it cannot extract the server's secret and generate cookies itself.
Why does it stop spoofing? A spoofed source never receives the SYN/ACK, so it does not know the cookie and cannot return a valid ACK.

The cost

Only 8 MSS values, and no room for TCP options (window scaling, SACK), so performance suffers. That is why Linux uses cookies only when the queue is full (net.ipv4.tcp_syncookies=1). Today options can be encoded in the timestamp.

The general pattern (anti-spoofing cookies): instead of creating state after message 1, send a hash of the connection data; the client returns it and proves it really is at that address. Also used in IKE (IPsec), DTLS and QUIC (Retry token).

7Beyond layer 4: connection floods, HTTP floods, low and slow

TCP connection flood

Bots complete full handshakes and send a short HEAD or leave the connection idle, over and over. Bypasses SYN proxies, but the attacker cannot spoof IPs, so the bots are exposed and the proxy can block or limit them.

Empty connection flood

Full connection, no data. The connection table is finite (~1500; Apache ships with 150 workers by default) and fills fast.

HTTP flood

A legitimate TCP connection + real requests, so very hard to detect. GET heavy pages (bandwidth), POST large bodies to forms (more effective: the server processes them). Always distributed, never spoofed.

Low and slow (Slowloris / R.U.D.Y.)

Partial requests: send one header line every few seconds and never finish. The server holds a thread per connection; when the table is full → DoS. Looks like a slow user; one attacker is enough.

Defense

Short timeouts for receiving headers (mod_reqtimeout), asynchronous servers (nginx) that do not allocate a thread per connection, per-IP connection limits, a WAF with rate limiting, CAPTCHA/JS challenges (Cloudflare "Under attack mode") against HTTP floods, and a CDN to absorb the load.

8RST attack and TCP connection spoofing

A TCP connection is defined by ports and sequence number. Ports are standard and Seq is guessable: guessing 32 bits is impractical, but stacks accept any Seq inside the window (because of packet loss). So send RSTs spaced one window apart: 232 / window attempts.

Watson (2004): the attack on BGP sessions. Big window + long-lived connection = easy. Windows client ports were sequential (most versions only up to 5000), so they were easy to guess.

Why BGP

A BGP session is a very long TCP connection between routers. An RST kills it, the router deletes every route learned from that neighbour, and the change propagates across the Internet (route flapping).

Defense

TCP MD5 signatures (RFC 2385) and TCP-AO for BGP sessions, GTSM (TTL = 255 so only a direct neighbour can send), and RFC 5961 (an RST inside the window but not at the exact position gets a challenge ACK).

9Bandwidth starvation and UDP floods

Flood bottlenecks with more traffic than they can carry, so legitimate traffic never reaches the target's infrastructure. Simply "pump" more than there is. UDP is connectionless: no handshake, no ACK, no flow control, so it is easy to spoof and flood.

UDP flood

Many UDP packets to random ports. For each one the server checks whether an application listens, finds none, and answers ICMP Destination Unreachable. Lots of CPU, full buffers.

Two profiles

Small packets to hammer the application (PPS), or large packets to exhaust bandwidth (BPS).

Example

A 30 Mb/s link to the server; the attacker sends 30 Mb/s of UDP. The link is full; with symmetric routing the replies also come back the same way.

Why it is hard to handle: spoofed addresses; you can flood without any "unwanted" traffic (every flow perfectly legitimate); and you can time many weak flows to cross the target link at once.

Three conditions for amplification

A UDP protocol (no handshake, so the source can be spoofed). A response much larger than the request. Many servers open to the world. And the victim sees traffic from legitimate servers, so blocking is hard without collateral damage.

Defense

At the reflector: close open resolvers, disable monlist, DNS response rate limiting, never expose memcached to the Internet. In the network: BCP 38 (no spoofing, no amplification). At the victim: cloud scrubbing centres (Cloudflare, Akamai) and anycast to spread the attack across many sites.

11DoS through routing: BGP

The Internet is a network of networks. An AS (autonomous system) is a set of IP networks under one administration (e.g. an ISP). BGP is the protocol by which ASes tell each other which prefixes they can reach.

Distance vector (RIP)

Each node keeps a distance vector and sends it to neighbours (Bellman-Ford). Split horizon: do not advertise a route out of the interface you learned it from.

Path vector (BGP)

Like distance vector, but each update carries the list of ASes on the path. Each router picks the "best" path (not necessarily the shortest: hot vs cold potato) and always prefers the most specific prefix.

Good news travels fast, bad news travels slowly: when a link fails, G1 and G2 keep advertising stale routes to each other and "count to infinity". Split horizon only prevents two-node loops.

The weakness

BGP messages have no authentication and no integrity protection. An attacker (or a mistake) can change prefixes and blackhole them, change the AS path to attract or divert traffic, or pass routes without permission (a multi-homed customer suddenly "providing transit" between two big ISPs). There is also an economic incentive: an ISP wants to dump traffic on others.

Defense today

RPKI (a cryptographic signature on "AS X may originate prefix Y", and route origin validation that drops invalid announcements), prefix filtering towards customers (MANRS), and BGPsec (signing the whole path, not yet common). The MyEtherWallet attack (2018) hijacked Amazon Route53 exactly this way to steal cryptocurrency.

12Advanced attacks: Shrew, CXPST, Coremelt, Crossfire, optimistic ACK

The new kind: do not attack the victim directly, attack the shared link its traffic crosses, or TCP's own control mechanisms.

Shrew: low-rate TCP-targeted attack

A shrew is a small mammal that attacks animals bigger than itself. TCP works on two time scales: RTT (10–100 ms, AIMD control) and RTO (retransmission timeout, minimum 1 s per RFC 2988). Under heavy loss the sender stops completely for an RTO, then restarts in slow start.

Model: a square wave with pulse length L, rate R, period T. When R plus existing traffic exceeds the link capacity, packets are lost. Choosing L > RTT and T slightly above minRTO synchronizes every TCP flow to the attack.

The principle

Shrew exploits homogeneity and determinism: every TCP reacts the same predictable way. There is a trade-off between predictability and vulnerability. Anti-DoS mechanisms target high rates, and detecting Shrew gives many false alarms from legitimate bursty flows. Proposed defense: randomize minRTO.

Attack on BGP sessions

BGP sends keepalives over TCP. A UDP flood on the R1–R2 link drops the keepalive, which is retransmitted after minRTO, then 2·minRTO... until the hold timer expires and the session drops.

CXPST

Coordinated cross-plane session termination: drop and restore selected links over and over → deliberate route flapping. Every change triggers recomputation and updates across the Internet and loads the CPUs of many routers.

Coremelt

1) Choose a target link. 2) Find pairs of bots whose traffic crosses it. 3) The bots send to each other. All traffic is wanted (the other bot wants it), no spoofing, no complaining victim.

Crossfire

Cuts off a whole area (N servers: an organization, a city, a country). 1) Traceroute from bots to public servers around the area, building a link map (72% stable). 2) Compute flow density and pick links. 3) Each bot sends a weak, legitimate flow to a public server; they add up on the target links. Rotate links before alarms trigger (moving target).

Optimistic ACKing

TCP rate depends on RTT. A malicious receiver ACKs data it has not received yet, faking a short RTT, so the server sends very fast. The sender has no strong way to detect it alone. With many such clients the server floods its own network.

Defense (beyond the slides)

Against optimistic ACK: nonces in ACKs (skip random segments and check the client did not "acknowledge" them). Against Crossfire/Coremelt: dynamic traffic engineering and rerouting, SDN that spots flows converging on a link.
