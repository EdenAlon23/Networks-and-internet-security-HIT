TCP: reliable, flow-controlled, congestion-controlled

TCP puts every mechanism from the previous chapter into one real protocol and adds two controls: flow control, so the sender never overruns the receiver, and congestion control, so all senders together never overrun the network. This chapter goes field by field through the segment, then through the timers, the handshake, and the congestion window, with the traces exams love to ask about.

3Sequence numbers and ACKs

TCP numbers bytes, not segments. The sequence number of a segment is the byte-stream number of its first data byte. The acknowledgement number is the seq # of the next byte expected from the other side (cumulative ACK). How the receiver handles out-of-order segments is not specified by the standard; in practice it buffers them.

Telnet echo (simple scenario)

Given

  • Host A's initial seq = 42, host B's = 79. The user types 'C'.

Solution

  1. A → B: Seq=42, ACK=79, data='C'
  2. B ACKs receipt of 'C' and echoes it back: Seq=79, ACK=43, data='C'
  3. A ACKs the echo: Seq=43, ACK=80 (no data)
  4. The ACK for B's data rode on A's data segment: piggybacking.
Exam trap

If a segment has Seq = 1000 and carries 500 bytes, the receiver's ACK is 1500 (not 1499, not 1001). SYN and FIN each count as one byte, so the ACK of a SYN with ISN x is x + 1.

4Round-trip time and timeout

How to set the timeout? It must be longer than the RTT, but the RTT varies. Too short → premature timeouts and unnecessary retransmissions; too long → slow reaction to segment loss. TCP measures SampleRTT (time from segment transmission until its ACK, ignoring retransmissions) and averages it with an exponential weighted moving average (EWMA):

EstimatedRTT  = (1 − α)·EstimatedRTT + α·SampleRTT          α = 0.125
DevRTT        = (1 − β)·DevRTT + β·|SampleRTT − EstimatedRTT|   β = 0.25
TimeoutInterval = EstimatedRTT + 4·DevRTT                          ("safety margin")

One update

Given

  • EstimatedRTT = 100 ms, DevRTT = 5 ms, new SampleRTT = 120 ms

Solution

  1. EstimatedRTT = 0.875·100 + 0.125·120 = 102.5 ms
  2. DevRTT = 0.75·5 + 0.25·|120 − 102.5| = 3.75 + 4.375 = 8.125 ms (the lecture/book order: update EstimatedRTT first, then use it; some exams use the old value, so state which)
  3. TimeoutInterval = 102.5 + 4·8.125 = 135 ms
  4. Initial TimeoutInterval is 1 s. After a timeout TCP doubles the interval (exponential backoff) until an ACK for new data arrives.

5TCP reliable data transfer

TCP creates a reliable service on top of IP's unreliable one with pipelined segments, cumulative ACKs and a single retransmission timer. Retransmissions are triggered by timeout events and by duplicate ACKs.

6Fast retransmit

The timeout period is often relatively long, which delays resending a lost packet. But a lost segment usually causes a stream of duplicate ACKs, because the segments after it still arrive. TCP fast retransmit: if the sender receives 3 additional ACKs for the same data ("triple duplicate ACKs", i.e. 4 identical ACKs in total), it resends the unACKed segment with the smallest seq # immediately, without waiting for the timeout. It is likely that this segment was lost, so don't wait.

Five segments, the second is lost

Given

  • Each segment carries 100 bytes, first seq = 92: seqs 92, 192, 292, 392, 492. Seq 192 is lost.

Solution

  1. 92 arrives → ACK 192
  2. 292 arrives (gap) → ACK 192 (dup #1); 392 → ACK 192 (dup #2); 492 → ACK 192 (dup #3)
  3. Third duplicate → the sender resends Seq=192 immediately.
  4. 192 arrives, fills the gap; the receiver had buffered 292–591 → ACK 592.

7Flow control

What if the network layer delivers data faster than the application reads from the socket buffer? The receive buffer overflows and data is lost. Flow control: the receiver controls the sender, so the sender won't overflow the receiver's buffer by transmitting too much, too fast.

rwnd = RcvBuffer − [LastByteRcvd − LastByteRead]          (free space in the receive buffer)
sender: LastByteSent − LastByteAcked ≤ rwnd               (unACKed "in-flight" data ≤ rwnd)
  • The receiver advertises its free buffer space in the receive window (rwnd) field of every segment it sends. RcvBuffer is set by socket options (typically 4096 bytes default; many OSes auto-tune it).
  • The sender limits the amount of unACKed data to rwnd, which guarantees the buffer will not overflow.
  • If rwnd = 0, the sender keeps sending 1-byte probe segments, so it learns when space frees up (otherwise both sides could wait forever).
  • The 16-bit field allows at most 65,535 bytes; the window scale option (RFC 7323) multiplies it by up to 214 for fast long links.
Remember

Flow control protects the receiver (rwnd, set by the receiver). Congestion control protects the network (cwnd, computed by the sender). The sender obeys both: LastByteSent − LastByteAcked ≤ min(cwnd, rwnd).

8Connection management

Why not a 2-way handshake?

With "request → accept", variable delays, retransmitted requests (because of message loss), message reordering, and not being able to see the other side all cause trouble. A retransmitted old req_conn can arrive after the client finished and left: the server opens a half-open connection with no client, and an old retransmitted data segment can even be accepted as new data. The 3-way handshake makes both sides agree on the connection and on both initial sequence numbers.

3-way handshake
  1. Client (state LISTEN → SYNSENT): chooses ISN x, sends SYN=1, Seq=x.
  2. Server (LISTEN → SYN RCVD): chooses ISN y, sends SYN=1, Seq=y, ACK=1, ACKnum=x+1, indicating it is alive and received the SYN.
  3. Client (→ ESTAB): receiving the SYNACK shows the server is live; sends ACK=1, ACKnum=y+1. This segment may already carry client-to-server data.
  4. Server (→ ESTAB): receiving the ACK shows the client is live.
Closing a connection
  1. Client sends FIN=1, seq=x (FIN_WAIT_1): it can no longer send but can still receive.
  2. Server replies ACK, ACKnum=x+1 (CLOSE_WAIT); client → FIN_WAIT_2. The server can still send data.
  3. Server sends FIN=1, seq=y (LAST_ACK).
  4. Client replies ACK, ACKnum=y+1 and enters TIME_WAIT for 2·MSL (maximum segment lifetime, e.g. 2×30 s), so a lost final ACK can be re-sent and old duplicates die out. Then CLOSED.

Simultaneous FIN exchange is allowed. A RST aborts a connection immediately, and a host that receives a SYN for a port with no listening socket replies with RST (this is what nmap reads as "closed", security chapter 03). A flood of SYNs that never complete the handshake is the SYN flood attack.

9Principles of congestion control

Congestion, informally: "too many sources sending too much data too fast for the network to handle". Manifestations: long delays (queueing in router buffers) and packet loss (buffer overflow). It differs from flow control: flow control is one sender too fast for one receiver.

Cost of congestionExplanation
Throughput can never exceed capacityTwo senders sharing a link of R: each gets at most R/2
Delay increases as capacity is approachedQueueing delay explodes as ρ → 1
Loss and retransmission decrease effective throughputThe link carries retransmitted copies instead of new data: offered load λ'in > λin
Unneeded duplicates decrease it furtherPremature timeouts send copies of packets that were only delayed
Upstream capacity is wastedWhen a packet is dropped at the last hop, every upstream link that carried it worked for nothing. With many multi-hop flows, throughput can collapse toward 0 (congestion collapse)

End-end congestion control

No explicit feedback from the network; congestion is inferred from observed loss and delay. This is TCP's approach.

Network-assisted

Routers give direct feedback to sending/receiving hosts: a congestion bit or an explicit rate. Examples: TCP ECN, ATM, DECbit.

10TCP congestion control

The sender keeps a congestion window cwnd and limits unACKed bytes to it. Roughly, it sends cwnd bytes, waits an RTT for ACKs, then sends more:

TCP rate ≈ cwnd / RTT  bytes/sec
MechanismRule
AIMD (additive increase, multiplicative decrease)Increase cwnd by 1 MSS every RTT until loss is detected; on loss, cut cwnd in half. The result is the "sawtooth" pattern: probing for bandwidth.
Slow startWhen a connection begins, cwnd = 1 MSS and it doubles every RTT (+1 MSS for every ACK received): the rate ramps up exponentially fast. Example: MSS = 500 bytes, RTT = 200 ms → initial rate 20 kbps.
ssthreshWhen cwnd reaches ssthresh, switch from exponential to linear growth (congestion avoidance). On a loss event, ssthresh is set to 1/2 of cwnd just before the loss.
Loss by timeoutssthresh = cwnd/2, cwnd = 1 MSS, back to slow start (both Tahoe and Reno).
Loss by 3 duplicate ACKsTCP Reno: ssthresh = cwnd/2, cwnd = ssthresh + 3 MSS, fast recovery (then linear). Dup ACKs show the network still delivers some segments, so the reaction is milder. TCP Tahoe: always cwnd = 1 MSS.
CUBIC (Linux default)After a loss at Wmax, grow cwnd as a cubic function of time: fast when far from Wmax, slow near it. Higher throughput than Reno on fast long paths.
Delay-based (BBR)Keep the pipe "just full but no fuller": measure the minimum RTT and the delivered rate, back off when RTT rises before loss happens. Used by Google.
ECNRouters mark 2 ECN bits in the IP header (ToS field) instead of dropping; the receiver echoes it with the ECE flag, and the sender halves cwnd as if a loss occurred.

Exam trap

Read the graph: an exponential segment = slow start; a straight line = congestion avoidance; a drop to half (+3) = triple duplicate ACK (Reno); a drop to 1 = timeout. Many textbooks simplify Reno's drop to exactly cwnd/2 (without the +3); follow the convention used in your lecture and say which one you used.

12Throughput and fairness

Average TCP throughput, ignoring slow start and assuming there is always data to send: if W is the window size (bytes) when loss occurs, the window oscillates between W/2 and W, so the average is 3/4 W per RTT:

avg throughput = (3/4) · W / RTT        bytes/sec
with loss rate L:  throughput ≈ 1.22 · MSS / (RTT · √L)

Example: to reach 10 Gbps with 1,500-byte segments and a 100 ms RTT you need W ≈ 83,333 in-flight segments and a loss rate of only about 2·10-10: one loss every 5 billion segments. That is why new versions of TCP (CUBIC, BBR) were needed for high speed.

Fairness goal: if K TCP sessions share the same bottleneck link of bandwidth R, each should get an average rate of R/K. AIMD achieves this: additive increase moves both connections along a 45° line, multiplicative decrease moves them toward the origin proportionally, so repeated cycles converge to the equal-share line.

  • Fairness holds under idealized assumptions: same RTT, a fixed number of sessions, only congestion avoidance. Shorter-RTT connections grab more.
  • UDP applications (multimedia) don't want their rate throttled, so they send at a constant rate and tolerate loss: not "TCP-friendly".
  • Parallel TCP connections: a link of rate R with 9 existing connections. A new app asking for 1 TCP gets R/10; asking for 11 TCPs gets 11/20 of R, more than half.

13Review

A segment has Seq = 500 and 200 bytes of data. What ACK number does the receiver send?

700, the number of the next byte it expects.

When does TCP retransmit without a timeout?

On 3 duplicate ACKs (fast retransmit).

rwnd is 0. What does the sender do?

Stops sending data but keeps sending 1-byte probe segments until the receiver advertises space again.

cwnd = 16 MSS when a timeout occurs. New ssthresh and cwnd?

ssthresh = 8, cwnd = 1 MSS, slow start.

Why does a 2-way handshake fail?

An old duplicate connection request can arrive after the client is gone, leaving a half-open connection that may accept old data.
