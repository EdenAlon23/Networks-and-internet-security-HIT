Chapter 04

Sniffing, spoofing and poisoning

How an attacker on a local network listens to traffic, forges addresses, and becomes a man in the middle by poisoning the MAC table, ARP, DHCP and DNS. Including the Kaminsky attack and how it was fixed. Each attack is broken down into the exact forged fields.

1Sniffing: listening to traffic

Wireshark is a packet sniffer and protocol analyzer: it captures frames and decodes them layer by layer. Usually needs admin rights. In promiscuous mode the NIC passes every frame on the segment to the OS, not only those addressed to its own MAC. Wireshark panes: menu, toolbar, filter bar, packet list, packet details (per layer), bytes (hex), status bar.

The threats

  • Listening to every packet on the segment
  • A silent attacker, almost undetectable
  • Works on many media, e.g. an Internet café
  • Can often become a MITM too

Why it is so easy

  • Plug and play with access to a shared medium
  • No special hardware
  • Supported by most NICs
What can be stolen

Any unencrypted protocol: Telnet, FTP, HTTP Basic, POP3/IMAP passwords; session cookies (session hijacking, e.g. Firesheep 2010); DNS queries (where people browse); NTLM hashes. Useful Wireshark filters: http.request, ftp || telnet, dns, tcp.flags.syn==1 && tcp.flags.ack==0, arp.opcode==2.

Defense

End-to-end encryption (TLS, SSH, VPN) makes sniffing worthless. On the network: switches instead of hubs, port security, 802.1X. You can try to detect a promiscuous NIC (send an ARP to a wrong MAC that only such a NIC would accept), but it is unreliable.

2Hub vs switch: topology decides what Eve sees

A switch learns by itself which MAC is on which port from the source address of every frame, and forwards each frame only to the right port. That gives collision-free performance and traffic isolation. So on a switched network Eve does not see Alice's and Bob's traffic, and must turn from "blind" into a MITM.

Degradation attack: MAC flooding

Some switches fall back to hub behaviour when the MAC table fills (CAM table overflow). The attacker sends thousands of frames with random source MACs (macof), the table fills, and the switch floods every frame to every port, including Eve's. See the animation.

Defense

Port security: limit the number of MAC addresses per port, shut the port down on violation.

4Blind TCP attacks: reset and hijacking

These appear in the lecture agenda without detailed slides; the explanation is mine. A TCP connection is identified by four values (IP and port of each side) plus the sequence number. A blind attacker who knows the addresses and ports only has to guess a Seq inside the receive window.

TCP connection reset

Inject a forged RST with Seq inside the window → the connection closes. 232 / window size = a feasible number of attempts. Also used for censorship (the Great Firewall sends RST to both sides).

TCP connection hijacking

Inject data with the right Seq → the other side accepts it as if it came from the sender (e.g. a command in a Telnet session). The famous case: Mitnick vs Shimomura (1994), when the ISN was predictable.

Defense

Random ISNs (RFC 6528), stricter RST checks (RFC 5961: an RST not exactly at the next Seq gets a challenge ACK), and encryption (TLS) so injected data is garbage that gets discarded.

5ARP: how an IP becomes a MAC

IP · layer 3

32 bits. Used to route to the destination network.

MAC · layer 2

48 bits, global space, usually burned into the NIC ROM. Used to move a frame between two nodes on the same physical network. FF:FF:FF:FF:FF:FF = broadcast.

Full packet format and the step-by-step exchange are in chapter 00 (ARP section and animation).

6ARP spoofing and ARP poisoning

The design flaw (RFC 826)

  • The ARP table is updated whenever a reply arrives.
  • Requests are not tracked: ARP is stateless, so replies are accepted without a question.
  • No authentication at all. Machines trust each other.

So a malicious machine can announce "the router's IP is at my MAC", and everyone who receives it believes it.

Method 1: unsolicited (gratuitous)

Send an ARP request with a forged sender IP, or an unrequested ARP reply. Many hosts update their table without asking. Good implementations ignore mappings they did not request.

Method 2: race the reply

Wait for (or predict, e.g. after DHCP) a real ARP request and answer before the real router. Improve the odds by loading the target so it answers slowly.

The forged packet, field by field
  1. Ethernet: dst = victim MAC, src = attacker MAC, EtherType 0x0806.
  2. ARP: opcode 2 (reply); sender MAC = attacker; sender IP = gateway IP; target MAC/IP = victim.
  3. The victim writes gateway IP → attacker MAC. The same packet with the roles swapped goes to the gateway.
  4. The attacker enables IP forwarding (sysctl net.ipv4.ip_forward=1) and repeats the replies every few seconds so the caches never heal.
  5. Every frame between victim and gateway now arrives at the attacker, who forwards it after reading or changing it. Note: the IP packets are untouched; only the layer-2 destination changed.
What happens next

Sniffing everything (even on a switched network), modifying content, SSL stripping (downgrading HTTPS to HTTP), local DNS spoofing, cookie theft, or simply dropping packets (DoS). Tools: arpspoof, Ettercap, Bettercap.

Solutions
  • Static entries (arp -s 192.168.0.65 00:50:ba:85:85:ca): solves it but almost unmanageable.
  • Detect one MAC mapped to several IPs (as in the diagram: …:03 appears for two addresses).
  • Monitoring tools: Arpwatch, XArp, Anti-arpspoof.
  • Ignore unsolicited mappings.
  • Port security on the switch, ARP rate limiting per port.
  • In practice: Dynamic ARP Inspection (DAI) on Cisco, which checks every ARP against the DHCP snooping table.

7DHCP and how it is used for attacks

What a "pirate" can do with a forged DHCP Offer

  • Rogue DHCP: answer faster than the real server with default gateway = attacker → MITM for all traffic leaving the network.
  • DNS server = attacker → controls every name-to-address lookup (perfect phishing).
  • DHCP starvation: send thousands of Discovers with random MACs (random chaddr) and drain the real server's pool (DoS); then the rogue server is the only one answering. Tools: Yersinia, DHCPig.
Defense

DHCP snooping on the switch: only ports configured as trusted (towards the real server) may send Offer/Ack; the rest are blocked. Plus port security against starvation.

8DNS and DNS poisoning

Routing uses IP addresses, but people and apps use hierarchical names (www.foo.edu). DNS maps names to addresses and also enables mobility, proximity, redundancy and load balancing (round robin).

Each cache entry: <name, value, type, TTL>. Types: A (name → IPv4), AAAA (IPv6), NS (domain → its name server), MX (incoming mail server). Message format: chapter 00.

Basic poisoning

The resolver sends a query with a 16-bit transaction ID and accepts the first matching answer. An off-path attacker sends many forged answers with different IDs, hoping to hit before the real one. If it works, the forged record is cached for all users until its TTL expires.

Why this was limited before 2008

If you missed, the real answer is cached for its TTL (say a day), and there is no new chance for that name until it expires. One attempt per day.

9The Kaminsky attack (2008)

The trick

Instead of attacking www.bank.com (already cached), ask each time for a new non-existent subdomain. No cache entry blocks retries, so you can try thousands of times in minutes. And what is injected is not the answer for the random name but an NS record in the Authority section: "the name server for all of bank.com is mine". The resolver accepts it (bailiwick: it is inside the queried domain), and from then on the whole domain is poisoned.

The fix

The ID field cannot grow to 32 bits without breaking the whole Internet. Instead every query uses a random source port and a random transaction ID: 216 × 216 = 232 ≈ 4.3 billion combinations to guess.

RFC 5452: hardening DNS against forged answers

  • Check the 16-bit ID and choose it randomly.
  • Verify Request.(SrcIP:port) = Response.(DstIP:port).
  • Choose a random source port, ideally from a pool of IP addresses too.
  • Accept answers only within a reasonable time.
  • None of this helps against a MITM, who sees the ID and the port.
The real solution

DNSSEC: every answer is digitally signed, with a chain of trust from the root. Even a MITM cannot forge a signature. DNS over HTTPS/TLS protects the client-to-resolver leg.

Real world

Kaminsky found the flaw in 2008 and coordinated a secret fix with all vendors before publishing. In 2018–2019 the DNSpionage / Sea Turtle campaign (linked to Iran) hijacked DNS of governments and companies in the Middle East, not by cache poisoning but by breaking into registrar accounts, changing NS records, and then getting valid TLS certificates for the hijacked domains (the Krebs article in the folder). In 2020 the SAD DNS attack showed how to discover the source port through an ICMP side channel.
