1Why email is insecure

Email is one of the most used services on the network, and it was originally designed with no security at all:

Confidentiality

Content can be read in transit: SMTP, POP3 and IMAP send cleartext. And the administrator of the destination server can read it too.

Authentication

Very easy to impersonate another sender. The From: field is just text.

Integrity

No guarantee the message was not modified on the way.

Email security areas per the lecture: viruses (server and desktop protection), hoaxes (common sense and training), spam (filters), and lack of confidentiality (S/MIME and PGP).

TLS on the way is not enough

STARTTLS encrypts each hop separately (link encryption from the symmetric chapter): every server on the path sees the mail, and an attacker can strip the STARTTLS command and downgrade to cleartext. PGP and S/MIME give end-to-end: only Alice and Bob.

Two separate "from" addresses exist. The envelope (MAIL FROM / RCPT TO commands) is what servers use for routing and bounces. The header (From:, To:, Subject: inside DATA) is what the user sees. Exploitation

Phishing and Business Email Compromise (a mail "from the CEO" to finance): per the FBI, the cybercrime with the highest financial losses, billions of dollars a year. Also lookalike domains (rn instead of m) and display-name spoofing ("CEO" <random@gmail.com>).

3Building secure mail in three stages

Stage A: confidentiality

Alice generates a random symmetric key KS, encrypts m with it (efficient), encrypts KS with Bob's public key, and sends KS(m) + KB+(KS). Bob opens KS with his private key, and m with it. This is exactly hybrid encryption.

Stage B: authentication and integrity

Alice signs: sends m in the clear + KA−(H(m)). Bob decrypts the signature with KA+, computes H(m) himself and compares.

Stage C: all together

Three keys are used: KA− (sign), KB+ (wrap the session key), KS (encrypt the body).

Why sign first, then encrypt

If you encrypt and then sign, an attacker can strip the signature and sign the ciphertext himself (without knowing what is inside), and appear as the sender. A signature inside binds the signer to the content itself, and it is also hidden from the eavesdropper (who sent to whom).

4PGP (Pretty Good Privacy)

Created by Phil Zimmermann (1991). The de-facto standard (others: S/MIME, MOSS, PGP/MIME). Free, worldwide, friendly, runs on many platforms, based on the best algorithms, and independent of government bodies. Used for email and file storage. Today mainly through the open implementation GnuPG (OpenPGP standard, RFC 4880).

History: the US government investigated Zimmermann for three years for "arms export" (strong crypto counted as munitions). He published the source code as a printed book, because a book is protected by the First Amendment.

5PGP operations

Authentication

  1. The sender creates a message.
  2. SHA-1 produces a 160-bit hash.
  3. The hash is encrypted with the sender's private key and attached.
  4. The receiver decrypts with the public key.
  5. The receiver computes the hash and compares. Equal → authentic.

Confidentiality

  1. The sender generates a random session key for this message only.
  2. Encrypts the message (AES, 3DES, IDEA, CAST-128).
  3. Encrypts the session key with RSA using the receiver's public key and attaches it.
  4. The receiver opens the session key with the private key.
  5. And decrypts the message.

Both services combined: encryption "wraps" the signing process (sign, then encrypt).

Why compression sits exactly there

After signing: sign the uncompressed message, so you do not need to recompress on every verification (and different compression implementations give different output).
Before encryption: less data to encrypt (faster), and safer, because a compressed message has less redundancy, so frequency analysis and the like are harder. (After encryption you cannot compress, because ciphertext looks random.)

Segmentation: mail protocols limit size (e.g. 50 KB), so PGP splits large messages and reassembles them on the other side before decryption and verification.

Full order on the sender: m → sign H(m) → ZIP → encrypt with KS (+ KS wrapped with KB+) → Radix-64 → segment. The receiver runs it in reverse.

6Radix-64: compatible with every mail system

PGP follows the "lowest common denominator": it does not assume the mail system can carry binary. Every 3 bytes (24 bits) are split into 4 groups of 6 bits, and each maps to an ASCII character (A–Z, a–z, 0–9, +, /). A CRC is added for error detection. The result is ~33% larger (4 characters per 3 bytes).

Worked example: bytes 4D 61 6E ("Man") = 010011 010110 000101 101110 = 19, 22, 5, 46 = TWFu.

A PGP message in an email looks like -----BEGIN PGP MESSAGE----- followed by a Radix-64 block. It is essentially Base64 (exactly the same idea as in MIME).

7Key management in PGP

Key ID

Instead of sending the whole public key with each message, send an ID: the low 64 bits of the key (KU mod 264). Almost certainly unique. Same for signatures.
Today fingerprints (160 bits) are used, because short key IDs (32 bits) were forged with collisions ("Evil 32", 2014).

Key rings

Public-key ring: all the public keys of others I know, indexed by key ID.
Private-key ring: my own key pairs, by key ID, encrypted with a hash of a passphrase.

Every user is a CA

Instead of an external CA, users sign keys of others they know: the web of trust. Trust in a key accumulates from who signed it (key-signing parties).

PGP weaknesses in the real world (beyond the slides)

EFAIL (2018): mail clients that render HTML: the attacker wraps an intercepted ciphertext in an <img src="http://evil/ tag, and the client decrypts and sends the plaintext in the URL. It abused the lack of integrity in CFB mode, and worked on S/MIME too.
SKS keyserver poisoning (2019): adding tens of thousands of junk signatures to a key crashed GnuPG.
Usability: "Why Johnny Can't Encrypt" (1999). Most people cannot use it correctly, so PGP stayed niche.

8S/MIME

Secure MIME, based on MIME. SMTP cannot carry binary files (images, Word, executables), non-ASCII characters (Hebrew, Arabic, Chinese), or messages above a certain size. MIME (an extension of RFC 822) encodes such content into ASCII. S/MIME adds cryptography to it, and it is PKI-based.

Enveloped data

Encrypted content + the related keys.

Signed data

The message encoded + a signed hash. Only someone with S/MIME can read it.

Clear-signed data

The original message in the clear + an encoded signature. Readable even without S/MIME (just not verifiable).

Signed & enveloped

Nesting of signed and encrypted.

9The defenses that actually work today against spoofing (beyond the slides)

PGP and S/MIME protect content, but most mail is not signed. So DNS-based, domain-level mechanisms became the standard (Gmail and Yahoo require them since 2024 for bulk senders):

SPF

A TXT record: which IP addresses may send mail for the domain.
v=spf1 include:_spf.google.com -all
Weakness: checks the envelope (MAIL FROM), not the From the user sees. Breaks on forwarding.

DKIM

The sending server signs headers and body with a private key; the public key is in DNS (selector._domainkey.example.com). A DKIM-Signature: header carries d= (domain), s= (selector), bh= (body hash), b= (signature). This is exactly "sign H(m)" from the previous chapter, at domain level.

DMARC

Policy: what to do when From fails SPF or DKIM alignment with the domain (none / quarantine / reject), and where to send reports.
v=DMARC1; p=reject; rua=mailto:...

  1. The receiving server gets the connection; it checks the connecting IP against the SPF record of the MAIL FROM domain.
  2. It fetches the DKIM public key from DNS (d= and s=) and verifies the signature over the listed headers and body hash.
  3. It checks alignment: does the domain that passed SPF or DKIM match the visible From: domain?
  4. If not, it applies the DMARC policy of the From: domain and records the result in an Authentication-Results: header.
More

MTA-STS and DANE (enforce TLS between servers, prevent STARTTLS stripping), BIMI (logo for domains with DMARC), spam and malware filtering (sandboxing attachments), and phishing training.

Real world

A quick check of any domain: dig TXT _dmarc.example.com. A domain without DMARC (or with p=none) is easy to spoof. This is also part of OSINT recon (chapter 02): MX and SPF records reveal which mail provider an organization uses.
