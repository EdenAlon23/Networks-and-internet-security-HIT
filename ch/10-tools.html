1Ground rules for the lab

Why this matters

Scanning or capturing traffic on networks you do not own or have permission to test is illegal in Israel (Computer Law 1995) and almost everywhere else. The lecturer's point in teaching these tools is that you understand what the packets look like, so you can recognise them as a defender. Build a lab: two or three VMs on a host-only network (e.g. VirtualBox), one of them running Wireshark.

2Wireshark and tcpdump: seeing the packets

Purpose: capture frames from an interface and decode every header, layer by layer. This is the tool that answers the lecturer's question "where does the packet go and what header does it have". The NIC is put in promiscuous mode, the kernel hands a copy of every frame to libpcap, and the tool decodes Ethernet → IP → TCP/UDP → application.

Filter typeSyntaxExample

sudo tcpdump -i eth0 -nn -c 20 'tcp[tcpflags] & tcp-syn != 0'
#   -i interface   -nn no name/port lookups   -c stop after 20 packets
# output line:  time  IP src.port > dst.port: Flags [S], seq N, win W, options [...]
#   [S]=SYN  [S.]=SYN/ACK  [.]=ACK  [R]=RST  [F.]=FIN/ACK  [P.]=PSH/ACK
How to read one packet in Wireshark
  1. Top pane: one line per frame (time, src, dst, protocol, info).
  2. Middle pane: the headers as a tree. Expand Ethernet II (dst MAC, src MAC, EtherType 0x0800), then Internet Protocol (TTL, ID, flags, offset, protocol 6/17/1), then TCP (ports, seq, ack, flags, window).
  3. Bottom pane: the raw bytes; clicking a field highlights its bytes.
  4. Statistics → Conversations and Follow → TCP Stream rebuild whole flows; Statistics → I/O Graph shows a flood as a spike.
Defense angle

Sniffing is passive and invisible on the wire. Defenses are switched networks with port security, 802.1X, and above all encryption (TLS, SSH, WPA2/3) so captured payloads are useless. Promiscuous-mode NICs can sometimes be spotted by sending a frame to a wrong MAC with a correct IP and seeing who answers.

4Shodan and Maltego: passive OSINT

Shodan

A search engine that scans the whole IPv4 space continuously and stores the banners it gets back (HTTP headers, SSH versions, TLS certificates, industrial protocols). You search its database, so no packet from you reaches the target. Filters like org:"Example Ltd", port:3389, ssl.cert.subject.cn:example.com.
Output: IP, open port, banner, product/version, location, sometimes known CVEs.

Maltego

A graph tool: you start from an entity (domain, person, email, IP) and run "transforms" that query public sources (DNS, whois, search engines, social networks) and draw the links. Shows the relations: domain → MX → IP → other domains on the same IP → email addresses → people.
Output: a graph you can export as a report.

Defense angle

Nothing to detect, because it is passive. Run Shodan on your own organization regularly (or use its monitor service) and remove what should not be public; keep staff information minimal on websites; use certificate transparency monitoring to see every certificate issued for your domains.

5netcat: raw TCP/UDP by hand

Purpose: "the TCP/IP Swiss army knife". It opens a TCP or UDP connection and connects it to your keyboard and screen, or listens on a port. The course uses it for banner grabbing: many services announce their name and version as soon as you connect.

nc -v 192.168.56.10 22          # connect; an SSH server sends its banner first
SSH-2.0-OpenSSH_8.9p1 Ubuntu-3

nc -v 192.168.56.10 80          # HTTP waits for us; type a request, then an empty line
HEAD / HTTP/1.0

HTTP/1.1 200 OK
Server: Apache/2.4.52 (Ubuntu)

nc -zv 192.168.56.10 20-25      # -z: only check if ports open, send no data
nc -l -p 4444                   # listen (on your own lab VM) to test a firewall rule

On the wire: a normal three-way handshake (SYN, SYN/ACK, ACK), the banner in the first data segment from the server, then FIN. Exactly what nmap -sT does, but by hand, one port at a time.

Defense angle

Hide or genericize version banners (ServerTokens Prod in Apache, server_tokens off in nginx), keep software patched so a leaked version is not useful, and alert on many short connections that read a banner and close.

Reading the output

open: a service is listening. closed: the host is up and answered RST, no service. filtered: something dropped the probe, i.e. a firewall rule exists. A mix of closed and filtered ports maps the firewall policy.

Defense angle

Close unused services, default-deny firewall (chapter 09) so most ports are "filtered", a stateful firewall so ACK/FIN/Xmas probes are dropped as INVALID, and an IDS (Snort, next sections) that alerts on one source touching many ports. Rate-limit and log.

7hping: one crafted packet at a time

Purpose: build a single TCP, UDP or ICMP packet with chosen header fields and show the reply, like ping but for any protocol. In the course it demonstrates ICMP message types (e.g. Information Request) and how a host answers specific flag combinations. It is the best way to see one header field change and watch the effect in Wireshark.

hping3 -S -p 80 -c 1 192.168.56.10     # one SYN to port 80 on your lab VM
#  reply: flags=SA → port open;  flags=RA → port closed
hping3 -1 -c 1 192.168.56.10           # ICMP echo (mode -1), like ping
hping3 -2 -p 53 -c 1 192.168.56.10     # one UDP packet to port 53
Reply fieldMeaning
flags=SASYN/ACK: listening
flags=RARST/ACK: closed
ttl=64 / 128typical Linux / Windows initial TTL (OS hint)
id=…IP ID; if it increments by 1 per packet, the host can act as an idle-scan zombie (chapter 03)
win=…TCP window, another OS hint
Defense angle

Stateful filtering drops crafted out-of-state packets; randomised IP IDs (modern OSes) stop idle scans; drop unusual ICMP types (Information/Timestamp/Address Mask requests) at the edge.

8Snort: the defender's view

Purpose: an open-source, rule-based IDS/IPS (signature, protocol and anomaly inspection). It sits where it can see traffic (span port or inline) and raises alerts. Components from the lecture:

  1. Packet decoder: takes packets from the interface and decodes the headers.
  2. Preprocessors: normalise traffic: reassemble IP fragments and TCP streams, detect port scans (sfPortscan). This is why fragmenting a scan (chapter 03 -f) does not hide it from Snort.
  3. Detection engine: the most important part; applies the rules to each packet.
  4. Logging and alerting: writes alerts and packets to files or a database.
  5. Output modules: send to syslog, a DB, a SIEM.
# action proto src_ip src_port -> dst_ip dst_port (options)
alert tcp any any -> $HOME_NET any (msg:"Xmas scan"; flags:FPU; sid:1000001; rev:1;)
alert tcp any any -> $HOME_NET any (msg:"NULL scan"; flags:0; sid:1000002; rev:1;)
alert icmp any any -> $HOME_NET any (msg:"ICMP to broadcast"; ip_proto:1; sid:1000003; rev:1;)
alert udp any 53 -> $HOME_NET any (msg:"Large DNS response"; dsize:>1400; sid:1000004; rev:1;)
Why rules on header fields work

Each rule option reads a specific header field: flags:FPU reads TCP byte 13, dsize the payload length, ttl, itype/icode the ICMP header. Scans and floods have header fingerprints (flags no real client uses, many SYNs without ACKs), which is exactly what chapter 03 and 05 taught.

Real world

Snort 3 and Suricata are the open-source standards; their alerts feed a SIEM. IDS sees, IPS also blocks (inline). Encrypted traffic limits payload rules, so header and flow rules matter more.

9ARP monitoring: arpwatch, XArp

The lecture lists software detection for ARP poisoning: arpwatch, XArp, anti-arpspoof. They keep a table of IP ↔ MAC pairs seen on the LAN and alert when a pair changes ("flip flop") or when one MAC claims many IPs (e.g. the gateway's IP suddenly answering from a laptop's MAC).

sudo arpwatch -i eth0          # logs to syslog:
# "flip flop 192.168.56.1 08:00:27:11:11:11 (08:00:27:22:22:22)"
arp -a                         # your own ARP cache: check the gateway's MAC
ip neigh show
Defense angle (chapter 04)

Dynamic ARP Inspection on the switch (checks ARP against DHCP snooping bindings), static ARP entries for critical hosts, port security, and encryption so a MITM sees only ciphertext. In Wireshark the display filter arp.duplicate-address-detected flags conflicting answers.

10openssl and gpg: checking the crypto chapters by hand

openssl s_client -connect example.com:443 -servername example.com
#   prints the certificate chain (subject, issuer), the TLS version and cipher suite
openssl x509 -in cert.pem -noout -text      # every X.509 field from chapter 07
openssl dgst -sha256 file.iso               # a hash, compare to the published value
openssl rand -hex 16                        # 128 random bits, e.g. an AES key or IV

gpg --gen-key                               # PGP key pair (chapter 08)
gpg --fingerprint alice@example.com         # verify this out of band
gpg --verify file.tar.gz.sig file.tar.gz    # check a signature (H(m) + public key)
gpg -e -s -r bob@example.com msg.txt        # sign then encrypt, as in chapter 08
dig TXT _dmarc.example.com +short           # DMARC policy
What to look for

In s_client: "Verify return code: 0 (ok)" means the chain reached a trusted root; the cipher line shows ECDHE (forward secrecy) and AES-GCM (AEAD). In x509: Validity dates, Subject Alternative Name, Signature Algorithm (sha256WithRSAEncryption, not md5/sha1).

11How the tools combine in an authorized assessment

The animation for this chapter shows the flow. Each step's output is the next step's input, and Wireshark runs throughout so you can see every probe:

Turning it around

The same chain is the defender's checklist: run it against your own network first, and every finding becomes a fix (chapter 09 rules, chapter 04 switch features, chapter 05 rate limits). Then confirm that Snort and the firewall logs actually recorded each phase. If they did not, the monitoring has a gap.
