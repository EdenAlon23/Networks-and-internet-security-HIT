פרק 00

יסודות ה-packet

כל שאר הקורס עוסק בניצול ובהגנה על ה-headers האלה, אז הפרק הזה עובר עליהם שדה אחרי שדה: מה כל שדה, למה הוא קיים, מי קורא אותו, ואיזו תקיפה משתמשת בו. כדאי לצפות קודם באנימציות, ואז להשתמש בתרשימים כמקור עזר.

לפני שמתחילים

ידע קדם מרשתות. הפרק הזה נשען על: N01 מחסנית 5 השכבות, N01 encapsulation, N08 ה-header של IPv4, N07 ה-segment של TCP, N10 ה-frame של Ethernet, N11 יום בחייה של בקשת web. אם משהו מאלה לא ברור, כדאי לקרוא אותו קודם בקורס רשתות תקשורת.

1שכבות, PDU וכתובות

כל שכבה מוסיפה header משלה לפני המידע שהיא מקבלת מלמעלה (encapsulation), והמקבל מסיר אותם בסדר הפוך (decapsulation). כל header עונה על שאלה אחת עבור רכיב אחד: ה-Ethernet header אומר ל-switch או לנתב הבא איזה מחשב בקו הזה, ה-IP header אומר לנתבים איזה מחשב באינטרנט, וה-TCP/UDP header אומר למערכת ההפעלה ביעד איזה תהליך.

למה שני סוגי כתובות

כתובות MAC שטוחות (בלי היררכיה), ולכן עובדות רק בתוך קו אחד. כתובות IP היררכיות (prefix של רשת + מחשב), ולכן נתבים יכולים לסכם מיליוני מחשבים ברשומת ניתוב אחת. לכן בכל קפיצה יש frame חדש (MAC חדשים) סביב אותו packet (אותן כתובות IP).

מפת הניצול

כמעט כל תקיפה בקורס מזייפת שדה אחד בשכבה אחת: MAC flooding מזייף MAC מקור בשכבה 2, ARP poisoning מזייף את המיפוי בין שכבה 2 ל-3, IP spoofing מזייף את המקור בשכבה 3, סריקות משחקות בדגלים של שכבה 4, ו-DNS poisoning מזייף תשובה בשכבה 7. מי שיודע מי קורא כל שדה, יודע את מי אפשר לרמות.

כתובת ה-MAC

48 ביט שנכתבים כ-6 בתים ב-hex, למשל 3c:22:fb:12:a4:01. 3 הבתים הראשונים הם ה-OUI (היצרן: 3c:22:fb = Apple), וכך סורקים מדפיסים את שם היצרן. ביט 0 של הבית הראשון = קבוצה (multicast/broadcast); ביט 1 = מנוהל מקומית (טלפונים עם MAC אקראי מדליקים אותו).

מה switch עושה עם כל frame

  1. לומד: כותב source MAC → incoming port בטבלת ה-CAM (עם טיימר התיישנות, בערך 300 שניות).
  2. מעביר: מחפש את ה-MAC של היעד. מוכר ← שולח רק מהפורט הזה. לא מוכר או broadcast ← מציף לכל הפורטים חוץ מזה שממנו הגיע.
  3. מסנן: אם היעד נמצא באותו פורט שממנו הגיע, זורק.
תקיפות בשכבה הזו
  • MAC flooding (macof): למלא את טבלת ה-CAM כך שה-switch מציף הכל (ראו את האנימציה בפרק 04).
  • MAC spoofing: לשנות את ה-MAC לכתובת מורשית כדי לעקוף סינון MAC או captive portal.
  • Broadcast storms: לולאות בלי STP מכפילות broadcasts עד שהרשת נעצרת.
הגנות

Port security (מקסימום MAC לפורט, sticky MAC), אימות 802.1X לכל פורט, חלוקה ל-VLAN, storm control, BPDU guard.

ARP packet: 28 בתים, נישא ישירות ב-Ethernet עם EtherType 0x0806. באדום: השדות שתוקף מזייף.

השלבים בדיוק
  1. מחשב A צריך לשלוח ל-192.168.1.20. הוא בודק את טבלת הניתוב: אותו subnet ← הקפיצה הבאה היא ‎.20 עצמו (אחרת הקפיצה הבאה היא ה-gateway, ו-A מפענח את ה-IP של ה-gateway).
  2. A מחפש ב-ARP cache (arp -a / ip neigh). אין.
  3. A שולח Request ב-broadcast: Ethernet dst ff:ff:ff:ff:ff:ff; ARP opcode 1, sender = ה-MAC/IP של A, target MAC = 00:00:00:00:00:00, target IP = ‎.20. ה-IP packet מחכה בתור.
  4. כל מחשב מקבל אותו. רק הבעלים של ‎.20 עונה; הוא גם שומר את המיפוי של A משדות ה-sender.
  5. B שולח Reply ב-unicast: opcode 2, sender = ה-MAC/IP של B, target = A.
  6. A שומר ‎.20 ← BB (ב-Linux רשומות הופכות ל-STALE אחרי בערך 30 שניות ונבדקות מחדש; ב-Windows בערך 15–45 שניות) ושולח את ה-packet שחיכה.

Gratuitous ARP: מחשב מכריז על המיפוי של עצמו בלי שביקשו (sender IP = target IP), למשל אחרי עלייה או failover, כדי שאחרים יעדכנו את ה-cache. זה לגיטימי, וזה בדיוק המנגנון ש-ARP poisoning מנצל.

למה כל כך קל לנצל ARP

ל-ARP אין אימות והוא בלי מצב: רוב המערכות מקבלות Reply שלא ביקשו ודורסות את ה-cache. התוקף שולח לקורבן "192.168.1.1 נמצא ב-MAC שלי" ול-gateway "192.168.1.10 נמצא ב-MAC שלי", והופך לאדם באמצע (פרק 04).

הגנות

Dynamic ARP Inspection (ה-switch בודק ARP replies מול טבלת ה-binding של DHCP snooping), רשומות ARP סטטיות למחשבים קריטיים, התראות IDS (arpwatch) על שינויי MAC, ומעל הכל הצפנה (TLS, SSH, IPsec) כך שה-MITM לא מקבל שום דבר קריא.

5פיצול והרכבה מחדש, בפירוט

לכל קו יש payload מקסימלי ל-frame, ה-MTU (Ethernet 1500, PPPoE 1492, הרבה מנהרות VPN בערך 1400). כשנתב צריך להעביר packet גדול מה-MTU של הקו הבא, יש לו שתי אפשרויות: לפצל (אם DF=0) או לזרוק ולדווח חזרה (אם DF=1). נתבי IPv4 מורשים לפצל; ב-IPv6 רק השולח.

פיצול: האלגוריתם המדויק (נתב או שולח)
  1. מקום למידע בכל fragment = MTU − אורך ה-IP header (1500 − 20 = 1480).
  2. מעגלים למטה לכפולה של 8, כי שדה ה-offset סופר בלוקים של 8 בתים (1480 כבר כפולה: 185 × 8).
  3. מעתיקים את ה-header המקורי לכל fragment. Identification, Source, Destination ו-Protocol נשארים זהים.
  4. קובעים Offset = (מיקום הבית של המידע של ה-fragment ב-payload המקורי) / 8.
  5. מדליקים MF=1 בכל fragment חוץ מהאחרון; האחרון שומר את ה-MF המקורי (בדרך כלל 0).
  6. קובעים Total Length של כל fragment ל-header + המידע שלו, ומחשבים מחדש את ה-checksum של כל header.
  7. options שמסומנים "copy" מועתקים לכל fragment; האחרים רק לראשון.

הרכבה ביעד: השלבים בדיוק
  1. מגיע packet עם MF=1 או Offset≠0 ← הוא fragment.
  2. מוצאים (או יוצרים) buffer הרכבה לפי (Source IP, Destination IP, Protocol, Identification), ומפעילים לו טיימר (RFC 791 מציע 15 שניות; Linux משתמש ב-30).
  3. מעתיקים את המידע של ה-fragment ל-buffer במיקום Offset × 8. רושמים אילו טווחים מולאו.
  4. ה-fragment עם MF=0 מגלה את אורך ה-payload הכולל = ה-Offset שלו × 8 + אורך המידע שלו.
  5. כשהאורך הכולל ידוע ואין חורים, בונים IP header אחד (Total Length = הגודל המלא, MF=0, Offset=0) ומעבירים את ה-datagram לפרוטוקול שבשדה Protocol.
  6. אם הטיימר נגמר קודם: זורקים הכל; אם fragment 0 הגיע, שולחים ICMP Time Exceeded, Code 1 (fragment reassembly time exceeded).

למה רק ביעד? fragments יכולים לעבור בנתיבים שונים, אז אין נתב שמובטח שיראה את כולם, והרכבה בכל קפיצה הייתה עולה זיכרון וזמן בליבת הרשת.

למה נמנעים מפיצול היום? אובדן fragment אחד = אובדן כל ה-datagram (אין שליחה חוזרת ברמת IP), firewalls לא רואים פורטים ב-fragments 2 והלאה, והרכבה עולה זיכרון. לכן TCP מדליק DF=1 ומשתמש ב-Path MTU Discovery: אם נתב עונה ICMP Type 3 Code 4 עם ה-MTU של הקפיצה הבאה, השולח מקטין את גודל ה-segment (MSS). אם firewall חוסם את ה-ICMP הזה, packets גדולים נעלמים בשקט: "PMTU black hole".

ניצול פיצול
  • Teardrop: fragments חופפים שגורמים לקוד הרכבה ישן לחשב אורך שלילי (פרק 05).
  • Ping of Death: Offset × 8 + length > 65,535 גולש מה-buffer.
  • fragments זעירים (nmap -f, --mtu 8): דגלי ה-TCP נופלים ב-fragment 2, אז filter שבודק רק את הראשון מפספס אותם.
  • דריסה בחפיפה: fragment מאוחר דורס בתים מוקדמים; אם ה-IDS והיעד פותרים חפיפות אחרת, הם רואים מידע שונה (insertion/evasion).
  • Fragment flood: לשלוח רק fragments ראשונים כדי למלא את ה-buffers של ההרכבה.
הגנות

Firewalls ו-IDS שמרכיבים לפני בדיקה ("virtual reassembly"), זריקת fragments קטנים ממינימום (RFC 1858) או חופפים (RFC 5722 אוסר חפיפות ב-IPv6), הגבלת זיכרון וזמן להרכבה, ומעבר חופשי ל-ICMP Type 3 Code 4 כדי ש-PMTUD יעבוד.

  2. שרת ← SYN+ACK, Seq = y, Ack = x+1. השרת שומר רשומה חצי-פתוחה (SYN-RCVD) ב-backlog.
  3. לקוח ← ACK, Seq = x+1, Ack = y+1. שניהם ESTABLISHED.
  4. מידע: ה-Seq של כל צד מתקדם במספר בתי ה-payload; Ack = הבית הבא שמצפים לו. SYN ו-FIN צורכים כל אחד מספר אחד.
  5. סגירה: FIN ← ACK, FIN ← ACK (ארבעה segments), ומי שסגר מחכה ב-TIME-WAIT למשך 2×MSL.

פורטים: השרת מאזין בפורט מוכר (0–1023, למשל 22, 25, 53, 80, 443); הלקוח משתמש בפורט זמני (Linux 32768–60999, Windows 49152–65535). חיבור מזוהה לפי ה-4-tuple (src IP, src port, dst IP, dst port), ואת זה NAT ו-stateful firewalls עוקבים אחריו.

Window: בקרת זרימה, כמה בתים נוספים המקבל יכול לשמור ב-buffer. ה-window ההתחלתי וסדר ה-options שונים בין מערכות הפעלה, ועל זה passive fingerprinting (p0f) מתבסס.

ניצול TCP
  • סריקות מנצלות את חוקי התגובה של ה-RFC: פורטים פתוחים עונים ל-SYN עם SYN/ACK, סגורים עם RST, ו-segments תועים של FIN/Null/Xmas מקבלים RST רק מפורטים סגורים (פרק 03).
  • SYN flood: רשומות חצי-פתוחות ממלאות את ה-backlog (פרק 05).
  • Session hijacking / RST injection: packet עם ה-4-tuple הנכון ו-Seq בתוך ה-window מתקבל. ISN אקראי (RFC 6528) הופך ניחוש עיוור ללא מעשי; תוקף שנמצא בדרך (אחרי ARP poisoning) עדיין יכול.

UDP header: רק 8 בתים.

אין לחיצת יד, אין sequence numbers, אין שליחה חוזרת, אין מצב חיבור. האפליקציה עושה את האמינות שהיא צריכה. זה הופך אותו למהיר ומתאים ל-DNS, DHCP, NTP, SNMP, VoIP/RTP, משחקים, QUIC.

ה-checksum מכסה גם pseudo-header (IP מקור, IP יעד, protocol, אורך), כך ש-packet שנמסר ל-IP הלא נכון מזוהה. ב-IPv4 הוא יכול להיות 0 (מבוטל); ב-IPv6 הוא חובה.

למה UDP הוא פרוטוקול ה-reflection

בלי לחיצת יד, השרת עונה לכל כתובת מקור שהבקשה טוענת. בקשה מזויפת של 60 בתים שגורמת לתשובה של 3,000 בתים הופכת שרתים למגברים שמכוונים לקורבן (DNS, NTP, SSDP, memcached; פרק 05). סריקת UDP איטית מאותה סיבה: פורט פתוח לעיתים קרובות לא אומר כלום.

ניצול DNS
  • Cache poisoning: הדברים היחידים שקושרים תשובה לשאילתה הם ה-ID של 16 ביט, פורט המקור והשאלה. מנחשים אותם לפני שהתשובה האמיתית מגיעה וה-resolver שומר את הרשומה שלך (פרק 04).
  • Amplification: שאילתות ANY/DNSSEC קטנות ומזויפות, תשובות גדולות (פרק 05).
  • Tunnelling / הוצאת מידע: מידע מקודד בתוויות של subdomain עובר את רוב ה-firewalls כי DNS תמיד מותר.
הגנות

אקראיות של פורט המקור, אימות DNSSEC, סגירת רקורסיה פתוחה, response rate limiting, הגבלת AXFR לשרתים משניים (+TSIG), וניטור שמות שאילתה ארוכים או עם אנטרופיה גבוהה.

DHCP הוא UDP בפורטים 67 (שרת) ו-68 (לקוח). נתבים מעבירים אותו בין subnets עם relay agent (ip helper-address, מוסיף option 82). חידוש קורה ב-50% מזמן החכירה (T1) ב-unicast לאותו שרת.

ניצול DHCP

Rogue DHCP: לענות מהר יותר מהשרת האמיתי ולחלק נתב ו-DNS משלך (option 3 ו-6) ← MITM לכל לקוח חדש. Starvation: אלפי Discovers עם chaddr אקראי מרוקנים את המאגר, לעיתים קרובות כצעד ראשון לפני הפעלת שרת זדוני.

הגנות

DHCP snooping (רק פורטי uplink מהימנים רשאים לשלוח Offer/Ack; הגבלת קצב Discovers לפורט), שגם בונה את טבלת ה-binding של IP-MAC ש-Dynamic ARP Inspection ו-IP Source Guard משתמשים בה.

11המסלול המלא: מקלידים http://example.com

כל packet, לפי הסדר
  1. DHCP (בעלייה): המחשב מקבל 192.168.1.10/24, gateway 192.168.1.1, DNS 192.168.1.1.
  2. ARP עבור ה-gateway: broadcast של "מי זה 192.168.1.1?"; תשובה עם ה-MAC של הנתב. נשמר ב-cache.
  3. DNS: UDP 192.168.1.10:53124 ← 192.168.1.1:53, ID 0x1a2b, "example.com A?". Ethernet dst = ה-MAC של הנתב. ה-resolver של הנתב עושה רקורסיה (root ← .com ← authoritative) ועונה 93.184.216.34.
  4. לחיצת יד TCP: SYN ל-93.184.216.34:80 מפורט זמני, DF=1, TTL 64, MSS 1460. הנתב הביתי עושה NAT: המקור הופך ל-IP הציבורי שלו ולפורט חדש; TTL 63.
  5. כל נתב באינטרנט: frame חדש, TTL−1, checksum מחושב מחדש, longest-prefix match. כתובות ה-IP והפורטים לא משתנים.
  6. SYN/ACK חוזר; ה-NAT ממפה אותו ל-192.168.1.10:הפורט הזמני; הלקוח שולח ACK.
  7. HTTP: PSH,ACK שנושא "GET / HTTP/1.1, Host: example.com". השרת מאשר ושולח "200 OK" ב-segment אחד או יותר (כל אחד ≤ MSS, ולכן בלי פיצול IP).
  8. הדפדפן מפרק את ה-HTML ופותח חיבורים נוספים לתמונות/CSS (לעיתים קרובות לשמות אחרים ← עוד DNS).
  9. החלפת FIN/ACK סוגרת את החיבור (או שהוא נשאר פתוח עם keep-alive).
עם HTTPS

אותו דבר עד שלב 7, אבל בפורט 443: קודם לחיצת יד TLS (ClientHello עם SNI = example.com גלוי, ServerHello, תעודה, החלפת מפתחות עם ECDHE, Finished), ואז HTTP בתוך records מוצפנים של TLS. מי שנמצא בדרך עדיין רואה כתובות IP, פורטים, גדלי packets, תזמון, שאילתות DNS (אלא אם DoH) ואת ה-SNI.

איפה תוקף יכול להיכנס

Rogue DHCP (שלב 1), ARP poisoning (שלב 2), DNS spoofing (שלב 3), האזנה לכל מה שגלוי (שלב 7 ב-HTTP), הזרקת TCP אם הוא בדרך. כל פרק בהמשך מפרק אחד מהשלבים האלה.
