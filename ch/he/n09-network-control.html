שכבת הרשת: מישור הבקרה

מישור הבקרה מחליט על המסלולים שמישור הנתונים עובר בהם. הפרק הזה פותר Dijkstra ו-Bellman-Ford ביד כמו שהמבחן שואל, מסביר למה האינטרנט משתמש ב-OSPF בתוך ארגון וב-BGP בין ארגונים, ומכסה את הפרוטוקולים ששומרים על הרשת נצפית: ICMP ו-SNMP, וגם את גישת בקר ה-SDN.

1ניתוב כבעיית גרף

המטרה של פרוטוקול ניתוב: לקבוע מסלולים "טובים" מהמחשבים השולחים למחשב המקבל, דרך רשת של נתבים. "טוב" אומר בדרך כלל עלות נמוכה, מהיר, או הכי פחות עמוס. האבסטרקציה: גרף G = (N, E) כש-N הם הנתבים ו-E הקווים; ca,b היא העלות של הקו הישיר בין a ל-b ‏(∞ אם הם לא שכנים ישירים). את העלות מגדיר מפעיל הרשת: היא יכולה להיות תמיד 1, ביחס הפוך לרוחב הפס, או לפי עומס.

סיווגאפשרויות
מידע גלובלי או מבוזר?גלובלי: לכל נתב יש את כל הטופולוגיה ועלויות הקווים ← אלגוריתמי link state. מבוזר: נתבים מכירים רק את השכנים ומחליפים מידע באיטרציות ← אלגוריתמי distance vector.
סטטי או דינמי?סטטי: מסלולים משתנים לאט (מוגדרים ידנית). דינמי: מסלולים משתנים מהר יותר, בעדכונים מחזוריים או בתגובה לשינויי עלות.

2ניתוב link state: האלגוריתם של Dijkstra

מרכזי: הטופולוגיה ועלויות הקווים ידועות לכל הצמתים, בעזרת "link state broadcast" (כל צומת מציף את עלויות הקווים שלו). כל צומת מחשב את המסלולים הזולים ביותר מעצמו ("המקור") לכל שאר הצמתים, וכך מקבל את טבלת ההעברה שלו. איטרטיבי: אחרי k איטרציות ידועים המסלולים הזולים ביותר ל-k יעדים.

Notation:  D(v) = current estimate of least-cost-path cost from source to v
           p(v) = predecessor node along the path from source to v
           N'   = set of nodes whose least-cost path is definitively known

Initialization:  N' = {u};  for all v: D(v) = c(u,v) if v adjacent to u, else ∞
Loop:  find w not in N' with minimum D(w); add w to N'
       for each neighbour v of w not in N':  D(v) = min( D(v), D(w) + c(w,v) )
until all nodes are in N'

3ניתוב distance vector: ‏Bellman-Ford

מבוסס על משוואת Bellman-Ford (תכנון דינמי). נסמן ב-Dx(y) את העלות של המסלול הזול ביותר מ-x ל-y. אז:

D_x(y) = min over neighbours v of x { c(x,v) + D_v(y) }

רעיון מרכזי: מדי פעם, כל צומת שולח לשכנים את הערכת ה-distance vector שלו. כש-x מקבל DV חדש משכן, הוא מעדכן את ה-DV שלו לפי משוואת B-F. בתנאים טבעיים ההערכה Dx(y) מתכנסת לעלות המינימלית האמיתית dx(y). כל צומת: מחכה (לשינוי בעלות קו מקומי או להודעה משכן) ← מחשב מחדש את ה-DV ← אם ה-DV ליעד כלשהו השתנה, מודיע לשכנים. האלגוריתם איטרטיבי ואסינכרוני (כל איטרציה מקומית נגרמת משינוי עלות מקומי או מהודעת עדכון DV), מבוזר ועוצר מעצמו (כל צומת מודיע רק כשה-DV שלו משתנה).

צעד Bellman-Ford אחד

  3. מתאים לתוצאה של Dijkstra ‏(4 דרך x), כמו שצריך.

שלושה צמתים, איטרציה מלאה

נתון

  • x–y 2, ‏y–z 1, ‏x–z 7. כל צומת מתחיל כשהוא מכיר רק את הקווים שלו.

פתרון

  1. t=0: ‏x: ‏[0, 2, 7], ‏y: ‏[2, 0, 1], ‏z: ‏[7, 1, 0] (עמודות x, ‏y, ‏z). כולם שולחים את הווקטור שלהם.
  2. t=1: ‏x מחשב Dx(z) = min{c(x,y) + Dy(z), c(x,z) + Dz(z)} = min{2 + 1, 7 + 0} = 3 ← x: ‏[0, 2, 3]. באופן דומה z: ‏Dz(x) = min{1 + 2, 7} = 3 ← z: ‏[3, 1, 0]. ‏y לא משתנה.
  3. t=2: ‏x ו-z שולחים את הווקטורים החדשים; אף ווקטור לא משתנה ← האלגוריתם עוצר.

4שינויי עלות: חדשות טובות מתפשטות מהר, רעות לאט

צמתים x, ‏y, ‏z עם c(x,y) = 4, ‏c(y,z) = 1, ‏c(x,z) = 50. בהתחלה Dy(x) = 4, ‏Dz(x) = 5 (דרך y).

העלות יורדת: 4 ← 1

t0: ‏y מזהה את השינוי, קובע Dy(x) = 1 ומודיע לשכנים. t1: ‏z מעדכן Dz(x) = 2 ושולח את ה-DV שלו. t2: ‏y מקבל אותו, שום דבר לא משתנה. שתי איטרציות: "חדשות טובות מתפשטות מהר".

העלות עולה: 4 ← 60

y רואה c(x,y) = 60 אבל z עדיין טוען Dz(x) = 5, אז y מחשב Dy(x) = min{60, 1 + 5} = 6 (מסלול דרך z שבעצם חוזר דרך y!). אז z מחשב min{50, 1 + 6} = 7, ‏y ← 8, ‏z ← 9 … 44 איטרציות עד ש-z מעדיף את הקו הישיר שלו של 50. זו בעיית ה-count-to-infinity; אם הקו x–y נופל לגמרי, זה באמת סופר לכיוון ∞.

לזכור

Poisoned reverse: אם z מנתב דרך y כדי להגיע ל-x, ‏z אומר ל-y שהמרחק שלו ל-x הוא ∞ (כדי ש-y לא ינתב ל-x דרך z). זה פותר לולאות בין שני צמתים אבל לא לולאות של שלושה צמתים או יותר. ‏RIP גם מגביל את "האינסוף" ל-16 קפיצות.

6ניתוב סקלבילי: מערכות אוטונומיות

מה שלמדנו עד עכשיו היה אידיאלי: כל הנתבים זהים, רשת "שטוחה". בפועל זה לא נכון: גודל (מיליארדי יעדים: אי אפשר לשמור את כולם בטבלאות, וההחלפה הייתה מציפה את הקווים) ואוטונומיה ניהולית (האינטרנט הוא רשת של רשתות; כל מנהל רוצה לשלוט בניתוב ברשת שלו).

הנתבים מאוגדים לאזורים שנקראים מערכות אוטונומיות (AS), או "domains". ניתוב Intra-AS רץ בין נתבים באותה AS; כל הנתבים ב-AS חייבים להריץ את אותו פרוטוקול; נתב gateway בקצה ה-AS מחובר לנתבים ב-ASes אחרות. ניתוב Inter-AS רץ בין ASes; נתבי ה-gateway מבצעים אותו (וגם ניתוב פנימי). טבלת ההעברה מוגדרת ע"י שניהם: הפנימי קובע רשומות ליעדים בתוך ה-AS, והחיצוני יחד עם הפנימי ליעדים חיצוניים.

7OSPF: ‏Open Shortest Path First

  • "Open": זמין לציבור. ‏link-state קלאסי: כל נתב מציף הודעות link-state של OSPF ‏(ישירות מעל IP ולא מעל TCP/UDP, פרוטוקול 89) לכל הנתבים ב-AS; לכל נתב יש את כל הטופולוגיה והוא משתמש ב-Dijkstra כדי לחשב את טבלת ההעברה.
  • אפשר כמה מדדי עלות: רוחב פס, השהיה.
  • אבטחה: כל הודעות OSPF מאומתות (כדי למנוע חדירה זדונית).
  • OSPF היררכי: היררכיה של שתי רמות, אזור מקומי ו-backbone. הודעות link-state מוצפות רק בתוך אזור או ב-backbone; לכל צומת יש טופולוגיה מפורטת של האזור שלו אבל הוא יודע רק את הכיוון ל-subnets באזורים אחרים. נתבי גבול אזור "מסכמים" מרחקים ליעדים באזור שלהם ומפרסמים ל-backbone; נתבי backbone מריצים OSPF רק ב-backbone; נתבי גבול מתחברים ל-ASes אחרות.

8BGP: ‏Border Gateway Protocol, הדבק שמחזיק את האינטרנט

BGP נותן לכל AS אמצעי: eBGP, לקבל מידע על אילו subnets נגישים מ-ASes שכנות; iBGP, להפיץ את המידע לכל הנתבים בתוך ה-AS; ולקבוע מסלולים "טובים" לרשתות אחרות לפי המידע ולפי מדיניות. הוא מאפשר ל-subnet לפרסם את קיומו, ואת היעדים שהוא יכול להגיע אליהם, לשאר האינטרנט: "אני פה, הנה למי אני יכול להגיע, ואיך". שני נתבי BGP ‏("peers") מחליפים הודעות BGP על חיבור TCP קבוע-למחצה (פורט 179).

בחירת מסלול ב-BGP (מסננים לפי הסדר)

  2. AS-PATH הקצר ביותר.
  3. נתב NEXT-HOP הקרוב ביותר: hot potato routing, בוחרים את ה-gateway המקומי עם העלות הפנימית הנמוכה ביותר (להוציא את ה-packet מה-AS שלך מהר ככל האפשר, בלי לדאוג לעלות החיצונית).
  4. קריטריונים נוספים.

דוגמת מדיניות: ‏A, ‏B, ‏C הם ספקים; ‏x, ‏w, ‏y לקוחות. ‏x מחובר לשני ספקים (dual-homed: ל-B ול-C). המדיניות: x לא רוצה להעביר תעבורה מ-B ל-C דרכו, ולכן x לא יפרסם ל-B מסלול ל-C. באופן דומה, B בוחר לא לפרסם את המסלול BAw ל-C: ‏B לא מרוויח כלום מניתוב CBAw, כי אף אחד מ-C, ‏A, ‏w אינו לקוח של B. "מעבירים תעבורה רק בשביל הלקוחות שלך."

בעולם האמיתי

ל-BGP אין בדיקה מובנית שה-AS באמת מחזיקה בקידומת שהיא מפרסמת. חטיפות BGP ‏(Pakistan Telecom שהפילה את YouTube ב-2008) ודליפות מסלולים עדיין קורות; ‏RPKI חותם איזו AS רשאית לפרסם איזו קידומת. ראו פרק 05 בקורס האבטחה.

9מישור הבקרה ב-SDN

למה מישור בקרה מרכזי לוגית? ניהול רשת קל יותר (פחות טעויות הגדרה בנתבים, גמישות רבה יותר בזרימות), העברה מבוססת טבלאות מאפשרת "לתכנת" נתבים, ומימוש פתוח ולא קנייני של מישור הבקרה מעודד חדשנות. דוגמה למשהו שקשה במסורתי: מפעיל רוצה שתעבורה מ-u ל-z תעבור ב-uvwz ותעבורה מ-x ל-z ב-xwyz; בניתוב לפי משקלי קווים צריך להגדיר מחדש משקלים, וחלק מהחלוקות בלתי אפשריות.

בקר SDN (מערכת ההפעלה של הרשת)מחזיק את מצב הרשת; מדבר עם אפליקציות הבקרה "מעליו" דרך northbound API ועם ה-switches "מתחתיו" דרך southbound API ‏(OpenFlow); ממומש כמערכת מבוזרת בשביל ביצועים, סקלביליות ועמידות (למשל ONOS, ‏OpenDaylight)

הודעות OpenFlow: מהבקר ל-switch ‏(features, ‏configure, ‏modify-state להוספה/מחיקה/שינוי של רשומות, ‏packet-out לשליחת packet מפורט מסוים); מה-switch לבקר (packet-in: העברת packet לבקר, ‏flow-removed, ‏port status). דוגמה למעגל המלא: ‏S1 מזהה נפילת קו ← שולח port status לבקר ← הבקר מעדכן את מידע ה-link-state ← ‏Dijkstra (אפליקציית הניתוב) מחשב מחדש ← הבקר מתקין flow tables חדשות ב-switches הרלוונטיים.

10ICMP: ‏Internet Control Message Protocol

משמש מחשבים ונתבים להעביר מידע ברמת הרשת: דיווח שגיאות (מחשב, רשת, פורט או פרוטוקול לא נגישים) ו-echo request/reply (שבהם ping משתמש). זה פרוטוקול של שכבת הרשת שרץ "מעל" IP: הודעות ICMP עוברות בתוך datagrams של IP ‏(פרוטוקול 1). להודעת ICMP יש type, ‏code, ועוד 8 הבתים הראשונים של ה-datagram שגרם לשגיאה (כדי שהשולח יוכל לשייך אותה לחיבור).

traceroute ו-ICMP בפירוט: המקור שולח סטים של segments של UDP ליעד (הסט הראשון TTL = 1, השני TTL = 2, …). ה-datagram בסט ה-n מגיע לנתב ה-n, שזורק אותו ושולח למקור ICMP type 11 code 0 עם השם וה-IP של הנתב. כשה-ICMP מגיע, המקור רושם את ה-RTT. תנאי העצירה: ה-segment של UDP מגיע בסוף למחשב היעד, שמחזיר ICMP ‏"port unreachable" ‏(type 3, ‏code 3). ראו את האנימציה ב-N02.

11ניהול רשת ו-SNMP

במערכות אוטונומיות יש אלפי רכיבי חומרה ותוכנה שמשפיעים זה על זה. ניהול רשת כולל ניטור, הגדרה ושליטה בהם. רכיבים: שרת מנהל (האפליקציה, עם מנהלי רשת אנושיים), מכשירים מנוהלים עם רכיבי חומרה ותוכנה שאפשר לנהל ולהגדיר, לכל אחד מידע (הגדרות, מצב, סטטיסטיקות), agent על כל מכשיר, ופרוטוקול ניהול רשת שהשרת משתמש בו כדי לשאול, להגדיר ולנהל מכשירים, והמכשירים משתמשים בו כדי לדווח לשרת על מידע ואירועים.

גישהאיך
CLIהמפעיל מקליד (או מריץ סקריפטים של) פקודות ישירות על כל מכשיר (למשל דרך ssh)
SNMP / MIBהמפעיל שואל/קובע מידע במכשיר (ה-MIB, ‏Management Information Base) בעזרת Simple Network Management Protocol מעל UDP (פורט 161 של ה-agent, ‏traps למנהל בפורט 162). שני מצבים: בקשה/תשובה (GetRequest, ‏GetNextRequest, ‏GetBulkRequest, ‏SetRequest ← Response) והודעות trap (ה-agent מודיע למנהל על אירוע חריג)
NETCONF / YANGגישה מופשטת והוליסטית ברמת כל הרשת: ניהול הגדרות של הרבה מכשירים, עם YANG כשפת מידול ו-NETCONF ‏(מעל תעבורה מאובטחת ואמינה כמו SSH/TLS) לשינויי הגדרות אטומיים בהרבה מכשירים
לזכור

SNMPv1/v2c מאמתים עם "community string" בטקסט גלוי (הרבה פעמים ברירת המחדל "public"), וזו מטרה קלאסית בסיור; ‏SNMPv3 מוסיף אימות והצפנה. ראו פרק 03 בקורס האבטחה.

12חזרה

ב-Dijkstra, איזה צומת נוסף ל-N' בכל צעד?

הצומת שעוד לא ב-N' עם ה-D(·) הנוכחי הקטן ביותר.

כתבו את משוואת Bellman-Ford.

Dx(y) = min על השכנים v של { c(x,v) + Dv(y) }.

למה חדשות רעות מתפשטות לאט ב-DV?

שכנים ממשיכים לפרסם עלויות נמוכות וישנות שמנתבות חזרה דרך הצומת עצמו, ולכן העלויות עולות רק בצעד אחד בכל החלפה (count-to-infinity).

למה משתמשים בפרוטוקולים שונים בתוך ASes וביניהן?

בפנים: מנהל אחד, אופטימיזציה של ביצועים (OSPF). ביניהן: מדיניות וגודל קובעים (BGP).

איזו הודעת ICMP מסיימת traceroute מבוסס UDP?

Type 3 code 3, ‏port unreachable, ממחשב היעד.
