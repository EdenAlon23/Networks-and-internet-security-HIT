שכבת האפליקציה ו-HTTP

הרצאה 3 מתחילה את הסיור מלמעלה למטה בשכבה שאנחנו משתמשים בה כל יום. קודם העקרונות שכל אפליקציית רשת חולקת (ארכיטקטורות, תהליכים ו-sockets, מה אפליקציה צריכה משכבת התעבורה), ואז HTTP במלואו: מבנה ההודעות, חשבון ה-RTT של חיבורים persistent ו-non-persistent, cookies, מטמונים, ואיך HTTP/2 ו-HTTP/3 פותרים את בעיית ה-head-of-line blocking.

1ארכיטקטורות של אפליקציות

אפליקציות רשת רצות רק על מחשבי הקצה; ליבת הרשת לא מריצה קוד של אפליקציות. זה מה שמאפשר לפרוס אפליקציות מהר: כותבים תוכנה לשני מחשבים, לא לכל נתב.

לקוח-שרת (client-server)

שרת: מחשב שתמיד דולק, כתובת IP קבועה, בדרך כלל ב-data center בשביל סקלביליות.

לקוחות: מדברים עם השרת, יכולים להתחבר ולהתנתק, יכולים לקבל IP דינמי, ולא מדברים ישירות זה עם זה.

דוגמאות: HTTP, ‏IMAP, ‏FTP.

Peer-to-peer (P2P)

אין שרת שתמיד דולק; מחשבי קצה כלשהם מתקשרים ישירות.

סקלביליות עצמית: peers חדשים מביאים גם קיבולת שירות חדשה, לא רק ביקוש.

ה-peers מתחברים ומתנתקים ומחליפים IP, ולכן הניהול מורכב. דוגמה: BitTorrent (פרק N05).

2תהליכים, sockets ומיעון

תהליך הוא תוכנה שרצה על מחשב. תהליכים במחשבים שונים מתקשרים ע"י החלפת הודעות. בכל session צד אחד הוא תהליך הלקוח (יוזם) והשני תהליך השרת (מחכה שיפנו אליו); באפליקציות P2P יש את שניהם.

תהליך שולח ומקבל הודעות דרך socket, הדלת בין האפליקציה לשכבת התעבורה. האפליקציה שולטת בכל מה שמעל הדלת; מערכת ההפעלה שולטת בתעבורה ומתחת.

כדי לפנות לתהליך צריך גם את כתובת ה-IP של המחשב (32 ביט) וגם מספר פורט (16 ביט), כי על מחשב אחד רצים הרבה תהליכים. פורטים מוכרים: HTTP 80, ‏HTTPS 443, ‏SMTP 25, ‏DNS 53, ‏IMAP 143.

פרוטוקול שכבת אפליקציה מגדיר: סוגי הודעות (בקשה, תשובה), תחביר (שדות ואיך מפרידים ביניהם), סמנטיקה (משמעות כל שדה), וכללים מתי ואיך שולחים ועונים. פרוטוקולים פתוחים מוגדרים ב-RFC ‏(HTTP, ‏SMTP); קנייניים לא (Skype, ‏Zoom).

השירות של TCP

זרם בתים אמין ובסדר, בקרת זרימה (לא להציף את המקבל), בקרת עומס (להאט כשהרשת עמוסה), מבוסס חיבור (handshake קודם).

לא מספק: תזמון, הבטחת תפוקה מינימלית, אבטחה.

השירות של UDP

datagrams לא אמינים ולא מסודרים. בלי הקמת חיבור, בלי בקרת זרימה או עומס, בלי שום הבטחות.

למה להשתמש בו? בלי השהיית handshake, בלי מצב חיבור, header קטן של 8 בתים, והאפליקציה שולטת בדיוק מתי המידע נשלח.

אבטחה: TLS

sockets רגילים של TCP ו-UDP שולחים טקסט גלוי, כולל סיסמאות. TLS מוסיף הצפנה, שלמות ואימות שרת מעל TCP, ממומש כספרייה באפליקציה (HTTPS = HTTP מעל TLS).

4ה-Web ו-HTTP

דף web הוא קובץ HTML בסיסי ועוד כמה אובייקטים שהוא מפנה אליהם (תמונות, סקריפטים, stylesheets), ולכל אחד יש URL: www.someschool.edu/someDept/pic.gif = שם מחשב + נתיב.

HTTP ‏(HyperText Transfer Protocol) הוא פרוטוקול הלקוח-שרת של ה-web. הלקוח (דפדפן) שולח בקשות; השרת שולח אובייקטים בתשובות. הוא רץ מעל TCP פורט 80 (HTTPS: ‏443): הלקוח פותח חיבור TCP, מחליפים הודעות HTTP, והחיבור נסגר.

HTTP הוא stateless (חסר מצב): השרת לא שומר מידע על בקשות קודמות של לקוח. פרוטוקולים ששומרים מצב מורכבים (צריך לשמור על עקביות אם לקוח או שרת קורסים). כשצריך מצב, מוסיפים אותו בעזרת cookies.

5HTTP ‏persistent מול non-persistent: חשבון ה-RTT

RTT (round-trip time): הזמן ש-packet קטן עובר מהלקוח לשרת וחזרה. הבאת אובייקט אחד על חיבור TCP חדש עולה: RTT אחד להקמת TCP ‏(SYN, ‏SYN-ACK), ‏RTT אחד לבקשת ה-HTTP ולבתים הראשונים של התשובה, ועוד זמן השידור של האובייקט.

Non-persistent response time per object = 2·RTT + file transmission time
מצבמה קורהזמן לבסיס + N אובייקטים (סדרתי)
Non-persistent ‏(HTTP/1.0)לכל היותר אובייקט אחד בכל חיבור TCP; החיבור נסגר אחרי כל תשובה. דפדפנים פותחים לעתים קרובות כמה חיבורים במקביל.2·RTT + N·2·RTT
Non-persistent, ‏P מקביליםקודם הבסיס, ואז N האובייקטים ב-⌈N/P⌉ סבבים של חיבורים מקבילים2·RTT + ⌈N/P⌉·2·RTT
Persistent בלי pipeliningהשרת משאיר את החיבור פתוח; הלקוח שולח בקשה חדשה רק אחרי שהתשובה הקודמת הגיעה2·RTT + N·RTT
Persistent עם pipeliningהלקוח שולח את כל הבקשות מיד כשהוא רואה את ההפניות2·RTT + 1·RTT (בערך RTT אחד לכולם)

(זמני השידור של האובייקטים מתווספים כשהשאלה לא אומרת להזניח אותם.)

דף עם 10 תמונות קטנות

נתון

  • RTT = 20 ms לשרת, שידור זניח. קובץ ה-HTML מפנה ל-10 תמונות באותו שרת. ה-DNS כבר במטמון.

פתרון

  1. Non-persistent, סדרתי: ‏2·20 + 10·2·20 = 440 ms
  2. Non-persistent, ‏5 מקבילים: ‏40 + ⌈10/5⌉·40 = 120 ms
  3. Persistent, בלי pipelining: ‏40 + 10·20 = 240 ms
  4. Persistent עם pipelining: ‏40 + 20 = 60 ms
  5. אם חיפוש ה-DNS לא היה במטמון ולקח RTT1 + … + RTTn, מוסיפים את זה פעם אחת בהתחלה.
מלכודת מבחן

סופרים חיבורים לפי שם המחשב, לא לפי IP. שני URLs עם שמות שונים שמתורגמים לאותו IP עדיין צריכים שני חיבורים persistent ב-HTTP/1.1, כי הדפדפן מנהל את מאגר החיבורים לפי host ‏(origin).

6מבנה הודעות HTTP

הודעות HTTP/1.x הן ASCII קריא. כל שורה מסתיימת ב-carriage return + line feed (\r\n), ושורה ריקה מפרידה בין ה-headers לגוף.

בקשה

GET /index.html HTTP/1.1\r\n             ← request line: method, URL path, version
Host: www-net.cs.umass.edu\r\n            ← header lines
User-Agent: Firefox/3.6.10\r\n
Accept: text/html,application/xhtml+xml\r\n
Accept-Language: en-us,en;q=0.5\r\n
Accept-Encoding: gzip,deflate\r\n
Connection: keep-alive\r\n
\r\n                                       ← blank line = end of headers
(body: empty for GET; form data for POST)

תשובה

HTTP/1.1 200 OK\r\n                         ← status line: version, code, phrase
Date: Tue, 08 Sep 2020 00:53:20 GMT\r\n
Server: Apache/2.4.6 (CentOS)\r\n
Last-Modified: Tue, 01 Mar 2016 18:57:50 GMT\r\n
ETag: "a5b-52d015789ee9e"\r\n
Accept-Ranges: bytes\r\n
Content-Length: 2651\r\n
Content-Type: text/html; charset=UTF-8\r\n
\r\n
<html>... 2651 bytes of data ...

אפשר להקליד את זה ידנית: telnet gaia.cs.umass.edu 80 (או nc), ואז להקליד את שורות הבקשה ושורה ריקה. זו הדרך הכי טובה לראות ש-HTTP הוא פשוט טקסט מעל חיבור TCP. עם curl -v http://example.com/ רואים את אותה החלפה.

8Cookies: שמירת מצב מעל פרוטוקול חסר מצב

ארבעה רכיבים: (1) header של Set-Cookie: בתשובת HTTP, ‏(2) header של Cookie: בבקשות HTTP הבאות, ‏(3) קובץ cookies במחשב המשתמש שהדפדפן מנהל, ‏(4) מסד נתונים בצד האתר.

צעד אחרי צעד
  1. סוזן נכנסת ל-amazon.com בפעם הראשונה. בבקשה אין cookie לאתר הזה.
  2. השרת יוצר מזהה 1678 ורשומה במסד הנתונים, ועונה עם Set-Cookie: 1678.
  3. הדפדפן שומר amazon 1678 בקובץ ה-cookies ושולח Cookie: 1678 בכל בקשה הבאה לאתר.
  4. השרת מבצע פעולה לפי ה-cookie (עגלת קניות, "מומלץ עבורך", להישאר מחובר). שבוע אחר כך אותו cookie עדיין נשלח.

שימושים: הרשאות, עגלות קניות, המלצות, מצב session. פרטיות: cookies מאפשרים לאתרים ללמוד הרבה עליכם. cookies של צד שלישי (שנקבעים ע"י פרסומת או tracker שמוטמע בהרבה אתרים, לא האתר שבו אתם נמצאים) מאפשרים לחברה אחת לעקוב אחריכם בין אתרים. דפדפנים חוסמים היום רבים מהם כברירת מחדל, וה-GDPR מתייחס למזהי cookie כמידע אישי.

9מטמון web (שרתי proxy)

מטמון web עונה לבקשות של לקוחות בלי לערב את השרת המקורי. הדפדפן מוגדר לשלוח את כל הבקשות למטמון; אם האובייקט במטמון, הוא חוזר מיד; אחרת המטמון מביא אותו מהשרת המקורי, שומר עותק ומחזיר אותו. המטמון הוא גם שרת (מול הלקוח) וגם לקוח (מול השרת המקורי). בדרך כלל ה-ISP או הארגון מתקינים אותו.

למה: זמן תגובה קצר יותר (המטמון קרוב יותר), פחות תעבורה על קו הגישה של הארגון, וזה מאפשר לספקי תוכן "עניים" להעביר תוכן ביעילות.

דוגמת מטמון: לשדרג את הקו או להתקין מטמון?

נתון

  • קו גישה 1.54 Mbps; ‏LAN ‏1 Gbps; ‏RTT מנתב הארגון לכל שרת מקורי: 2 s
  • אובייקטים של 100 kbit; הדפדפנים מבקשים בממוצע 15 אובייקטים בשנייה ← 1.5 Mbps של מידע

פתרון

  1. ניצולת קו הגישה = 1.5 / 1.54 = 0.97 ← השהיות תור של דקות. השהיה כוללת ≈ השהיית האינטרנט + דקות + מיקרו-שניות.
  2. אפשרות 1, לקנות קו של 154 Mbps: ניצולת 0.0097, סה"כ ≈ 2 s + ms + μs. יקר.
  3. אפשרות 2, להתקין מטמון עם hit rate של 0.4: רק 60% מהבקשות עוברות בקו ← 0.6 × 1.5 = 0.9 Mbps, ניצולת 0.9 / 1.54 = 0.58 ← השהיה קטנה.
  4. השהיה ממוצעת = 0.6 × (≈2.01 s מהשרת המקורי) + 0.4 × (≈ms מהמטמון) ≈ 1.2 s. נמוך יותר מאשר עם הקו המהיר, וזול.

10GET מותנה

המטרה: לא לשלוח את האובייקט אם במטמון כבר יש עותק עדכני. המטמון שם בבקשה את התאריך של העותק שלו; השרת עונה בלי גוף אם שום דבר לא השתנה.

cache → server   GET /fruit/kiwi.gif HTTP/1.1
                  Host: www.exotiquecuisine.com
                  If-Modified-Since: Wed, 9 Sep 2015 09:23:24

server → cache   HTTP/1.1 304 Not Modified          (no body: saves bandwidth)
          or     HTTP/1.1 200 OK  + the new object  (it did change)

ETag + If-None-Match עושים את אותו הדבר עם מזהה גרסה במקום תאריך. Cache-Control: max-age=3600 אומר למטמונים שהאובייקט טרי לשעה, כך שהם לא צריכים לשאול בכלל בזמן הזה.

11HTTP/2 ו-HTTP/3

HTTP/1.1 משרת בקשות לפי הסדר, מי שבא ראשון מקבל ראשון (FCFS) על חיבור. אובייקט גדול (וידאו) בראש התור גורם לאובייקטים קטנים שאחריו לחכות: head-of-line (HOL) blocking. גם שחזור אובדן (שידור חוזר ב-TCP) עוצר את כל מה שאחרי ה-segment שאבד.

גרסהשינויים עיקריים
HTTP/1.0 (1996)Non-persistent כברירת מחדל; אובייקט אחד לכל חיבור TCP
HTTP/1.1 (1997)חיבורים persistent כברירת מחדל, pipelining (כמעט לא בשימוש), header ‏Host: חובה (כמה אתרים על שרת אחד), העברה ב-chunks, מטמון טוב יותר
HTTP/2 (2015)מסגור בינארי: אובייקטים מחולקים ל-frames ו-frames של אובייקטים שונים משולבים על חיבור TCP אחד, כך שאובייקטים קטנים לא נתקעים מאחורי גדולים. עדיפויות שהלקוח קובע, server push של אובייקטים שהלקוח עוד לא ביקש, דחיסת headers ‏(HPACK).
HTTP/3 (2022)רץ מעל QUIC, שרץ מעל UDP. ‏QUIC מוסיף אמינות, בקרת עומס ו-TLS 1.3 מובנה לכל stream בשכבת האפליקציה, כך ש-packet שאבד עוצר רק את ה-stream שלו (בלי HOL blocking בין streams), והקמת החיבור והאבטחה לוקחת RTT אחד (0-RTT בחידוש).
למה

למה HTTP/3 עבר ל-UDP? ‏TCP ממומש בגרעין מערכת ההפעלה ובקופסאות ביניים ברשת, ולכן לשנות אותו לוקח עשור. בניית הלוגיקה החדשה של התעבורה במרחב המשתמש מעל UDP מאפשרת לדפדפנים ולשרתים לפרוס אותה מיד.

12חזרה

למה צריך גם כתובת IP וגם פורט כדי להגיע לתהליך?

ה-IP מזהה את המחשב; רצים עליו הרבה תהליכים, ולכן הפורט מזהה את ה-socket של התהליך הנכון.

כמה זמן לוקח להביא אובייקט אחד ב-HTTP ‏non-persistent?

2·RTT + זמן שידור: RTT אחד ל-handshake של TCP, ואחד לבקשה ולתשובה.

מה המשמעות של 304, ומתי שולחים אותו?

Not Modified: התשובה ל-GET מותנה כשהעותק במטמון עדיין עדכני. אין לה גוף.

איך שרת חסר מצב זוכר את העגלה שלכם?

Set-Cookie נותן לכם מזהה; הדפדפן מחזיר אותו ב-header של Cookie והשרת מחפש את המזהה במסד הנתונים שלו.

איזו בעיה HTTP/2 פותר, ומה HTTP/3 מוסיף?

HTTP/2 משלב frames כדי להימנע מ-HOL blocking בין אובייקטים; ‏HTTP/3 ‏(QUIC מעל UDP) נמנע גם מ-HOL blocking שנגרם משחזור אובדן ב-TCP, ומאחד את ה-handshake של התעבורה ושל TLS.
