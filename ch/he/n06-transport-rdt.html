שכבת התעבורה והעברת נתונים אמינה

הרצאות 5–6 יורדות לשכבת התעבורה: איך מחשב אחד משרת הרבה תהליכים (multiplexing), מה UDP מוסיף מעל IP (כמעט כלום, בכוונה), איך ה-checksum שלו עובד, ואז השאלה המרכזית של הקורס: איך בונים ערוץ אמין מעל ערוץ לא אמין. בונים את הפרוטוקול צעד אחרי צעד, מ-rdt 1.0 עד rdt 3.0, מודדים למה stop-and-wait איטי מדי, ומתקנים עם pipelining: ‏Go-Back-N ו-Selective Repeat.

1שירותים ופרוטוקולים של שכבת התעבורה

שכבת התעבורה מספקת תקשורת לוגית בין תהליכי אפליקציה שרצים במחשבים שונים. היא רצה רק במחשבי הקצה: השולח מפרק הודעות אפליקציה ל-segments ומעביר אותם לשכבת הרשת; המקבל מרכיב את ה-segments בחזרה להודעות ומעביר למעלה. שכבת הרשת, לעומת זאת, מספקת תקשורת לוגית בין מחשבים.

למה

האנלוגיה מההרצאה: בית עם 12 ילדים שולח מכתבים לבית עם 12 ילדים. מחשבים = בתים, תהליכים = ילדים, הודעות אפליקציה = מכתבים במעטפות, פרוטוקול שכבת הרשת = הדואר, פרוטוקול התעבורה = אן וביל, שאוספים את המכתבים מהילדים בבית ומחלקים את אלה שמגיעים (multiplexing ו-demultiplexing). אן וביל עובדים רק בתוך הבתים; הם לא יכולים להאיץ את משאית הדואר.

פעולות השולח: לקבל את ההודעה מהאפליקציה, לקבוע את ערכי שדות ה-header, ליצור segment, להעביר ל-IP. פעולות המקבל: לקבל את ה-segment מ-IP, לבדוק את ערכי ה-header, לחלץ את הודעת האפליקציה, ולעשות demultiplexing למעלה לאפליקציה דרך ה-socket.

2Multiplexing ו-demultiplexing

Multiplexing אצל השולח: לאסוף מידע מכמה sockets ולהוסיף header של תעבורה (שישמש אחר כך ל-demultiplexing). Demultiplexing אצל המקבל: להשתמש במידע ב-header כדי למסור כל segment שהגיע ל-socket הנכון. המחשב מקבל datagrams של IP; בכל אחד יש כתובת IP מקור ויעד ו-segment תעבורה אחד עם פורט מקור ויעד.

בלי חיבור (UDP)

socket של UDP מזוהה ע"י הזוג (IP יעד, פורט יעד). כל ה-datagrams עם אותו פורט יעד הולכים לאותו socket, גם אם הם מגיעים מכתובות IP או פורטים שונים. פורט המקור הוא "כתובת ההחזרה" שהשרת משתמש בה כדי לענות.

דוגמה מההרצאה: A ‏(פורט 9157) ו-C שולחים שניהם לפורט 6428 של B ← socket אחד ב-B. ‏B כבר לא יודע "מי זה מי" מה-socket לבדו.

מבוסס חיבור (TCP)

socket של TCP מזוהה ע"י הרביעייה (IP מקור, פורט מקור, IP יעד, פורט יעד). המקבל משתמש בכל ארבעת הערכים כדי לנתב את ה-segment. שרת תומך בהרבה sockets של TCP בו-זמנית, אחד לכל לקוח מחובר, כולם על אותו פורט שרת.

דוגמה: שלושה לקוחות מתחברים לשרת web בפורט 80 ← שלושה sockets שונים. אם אפילו ערך אחד מהארבעה שונה, זה socket אחר. ‏HTTP ‏non-persistent פותח socket חדש לכל בקשה.

3UDP: ‏User Datagram Protocol ‏(RFC 768)

UDP הוא פרוטוקול "בלי קישוטים": segments יכולים לאבוד או להגיע לא בסדר, ואין handshake ואין מצב לכל חיבור. למה להשתמש בו? בלי הקמת חיבור (בלי השהיית RTT), פשוט (בלי מצב בשולח או במקבל), header קטן (8 בתים), ובלי בקרת עומס, אז אפשר לשלוח מהר ככל שרוצים. אמינות, אם צריך, מוסיפים בשכבת האפליקציה.

משתמשים בו: מולטימדיה בסטרימינג (סובלני לאובדן, רגיש לקצב), DNS, ‏SNMP, ‏HTTP/3 ‏(QUIC מוסיף אמינות ובקרת עומס מעל UDP).

4ה-checksum של האינטרנט

המטרה: לזהות שגיאות (ביטים שהתהפכו) ב-segment. השולח מתייחס לתוכן ה-segment ‏(header, מידע, ו-pseudo-header עם כתובות ה-IP) כרצף של מספרים של 16 ביט, מחבר אותם בחשבון משלים ל-1, ושם את המשלים של הסכום בשדה ה-checksum. המקבל מחבר את כל המילים של 16 ביט כולל ה-checksum: התוצאה חייבת להיות כולה 1 ‏(0xFFFF). אם לא, זוהתה שגיאה.

חיבור שתי מילים של 16 ביט

נתון

  • מילה 1 = 1110 0110 0110 0110, מילה 2 = 1101 0101 0101 0101

פתרון

  1. סכום בינארי: ‏1 1011 1011 1011 1011 ‏(17 ביט: נשא מהביט העליון)
  2. Wraparound: מחברים את הנשא בחזרה לביט הנמוך: ‏1011 1011 1011 1011 + 1 = 1011 1011 1011 1100
  3. Checksum = משלים ל-1 (הופכים כל ביט): 0100 0100 0100 0011
  4. המקבל: סכום + checksum = 1011 1011 1011 1100 + 0100 0100 0100 0011 = 1111 1111 1111 1111 ✓
מלכודת מבחן

ה-checksum רק מזהה; הוא אף פעם לא מתקן. והוא חלש: אם מילה אחת מקבלת +1 בביט מסוים ומילה אחרת מאבדת אותו באותו מיקום (שני היפוכים שמבטלים זה את זה), הסכום לא משתנה והשגיאה לא מזוהה. למה צריך אותו ב-UDP אם בשכבת הקו יש CRC? עקרון קצה-לקצה: לא כל קו בודק שגיאות, וביטים יכולים להשתבש גם בזיכרון של נתב.

5בניית העברה אמינה: rdt 1.0 עד 3.0

הממשקים: האפליקציה קוראת ל-rdt_send(data); צד השולח קורא ל-udt_send(pkt) כדי לדחוף packet על הערוץ הלא אמין; בהגעה נקראת rdt_rcv(pkt); המקבל קורא ל-deliver_data(data) כדי להעביר את המידע למעלה. מתארים את השולח והמקבל עם מכונות מצבים סופיות (FSM): אירוע / פעולות על כל מעבר. מורכבות הפרוטוקול תלויה לגמרי במה שהערוץ יכול לעשות לא נכון.

6למה stop-and-wait איטי מדי

ניצולת Usender היא החלק מהזמן שבו השולח עסוק בשליחה. ב-stop-and-wait השולח משדר packet אחד (L/R), ואז מחכה RTT שלם ל-ACK:

U_sender = (L/R) / (RTT + L/R)

קו 1 Gbps, השהיית התפשטות 15 ms

נתון

  • R = 1 Gbps, התפשטות בכיוון אחד 15 ms ← RTT = 30 ms, ‏packet ‏L = 8,000 ביט (1 KB)

פתרון

  1. dtrans = L/R = 8,000 / 109 = 8 μs
  2. U = 0.008 ms / 30.008 ms = 0.00027
  3. תפוקה = L / (RTT + L/R) = 8,000 ביט / 30.008 ms ≈ 267 kbps על קו של 1 Gbps!
  4. הפרוטוקול, ולא הקו, מגביל את הביצועים.

Pipelining: השולח מרשה כמה packets "בדרך" שעוד לא אושרו. עם N חבילות ל-RTT: U = N·(L/R) / (RTT + L/R) (כל עוד זה ≤ 1). עם N = 3 בדוגמה, ‏U = 0.00081, פי שלושה טוב יותר. כדי למלא את הצינור לגמרי, N·L צריך להיות בערך R·RTT (מכפלת רוחב הפס בהשהיה). Pipelining דורש טווח של מספרי רצף (לא רק 0/1) ו-buffers אצל השולח ו/או המקבל. שתי צורות כלליות: ‏Go-Back-N ו-Selective Repeat.

7Go-Back-N (GBN)

  • שולח: חלון של עד N חבילות רצופות ששודרו ועוד לא אושרו, עם מספר רצף של k ביט ב-header. מצביעים: send_base (הישן ביותר שלא אושר) ו-nextseqnum (הבא לשליחה).
  • ACK מצטבר: ‏ACK(n) מאשר את כל החבילות עד מספר רצף n כולל. כשמקבלים ACK(n), מזיזים את החלון קדימה כך שיתחיל ב-n+1.
  • טיימר אחד ל-packet הישן ביותר בדרך. ב-timeout(n): משדרים שוב את packet n ואת כל החבילות עם מספר רצף גבוה יותר בחלון ("חזור N אחורה").
  • מקבל: רק ACKs. תמיד שולח ACK על ה-packet התקין עם מספר הרצף הגבוה ביותר שהגיע בסדר; זה יכול לייצר ACKs כפולים. הוא צריך לזכור רק את rcv_base (מספר הרצף הצפוי).
  • ב-packet שלא בסדר: זורקים אותו (בלי buffer אצל המקבל) ושולחים שוב ACK על מספר הרצף הגבוה ביותר שבסדר.

GBN עם N = 4, ‏pkt2 אבד

נתון

  • השולח שולח pkt0 עד pkt3 (החלון מלא).

פתרון

  1. המקבל מקבל 0 ← ack0, ‏1 ← ack1; ‏pkt2 אבד; מקבל 3 ← לא בסדר: זורק, ושולח שוב ack1.
  2. ack0 ו-ack1 מזיזים את החלון: השולח שולח pkt4 ו-pkt5. המקבל זורק את שניהם ושולח ack1, ‏ack1.
  3. pkt2 מגיע ל-timeout ← השולח משדר שוב את pkt2, ‏pkt3, ‏pkt4, ‏pkt5.
  4. המקבל מקבל עכשיו את 2, 3, 4, 5 בסדר ומאשר כל אחד.
לזכור

מגבלת גודל החלון ב-GBN עם מספרי רצף של k ביט: N ≤ 2k − 1. עם N = 2k, אם כל ה-ACKs של חלון מלא אבדו, המקבל לא יכול להבדיל בין חלון ישן ששודר שוב לבין חלון חדש.

8Selective Repeat (SR)

  • המקבל מאשר בנפרד כל packet שהתקבל תקין, ושומר ב-buffer חבילות שהגיעו לא בסדר, כדי למסור אותן בסדר לשכבה העליונה בהמשך.
  • השולח מחזיק טיימר לכל packet שלא אושר; ב-timeout הוא משדר שוב רק את ה-packet הזה.
  • חלון השולח: N מספרי רצף רצופים. ACK(n) בתוך החלון מסמן את n כהתקבל; אם n הוא הקטן ביותר שלא אושר, החלון מתקדם למספר הרצף הבא שלא אושר.
  • מקבל: ‏pkt n בטווח [rcv_base, rcv_base+N−1] ← שולח ACK(n); אם לא בסדר, שומר ב-buffer; אם בסדר, מוסר אותו ואת כל החבילות השמורות שבסדר, ומקדם את החלון. ‏pkt n בטווח [rcv_base−N, rcv_base−1] (כבר נמסר) ← עדיין שולח ACK(n), כי ייתכן שהשולח לא קיבל את ה-ACK הקודם. אחרת מתעלם.

SR עם N = 4, ‏pkt2 אבד

נתון

  • השולח שולח pkt0 עד pkt3.

פתרון

  1. מקבל: 0 ← מוסר, ack0; ‏1 ← מוסר, ack1; ‏3 ← שומר ב-buffer, ‏ack3.
  2. שולח: ack0, ‏ack1 מזיזים את החלון ← שולח pkt4, ‏pkt5. ‏ack3 נרשם (החלון עוד לא יכול לעבור את 2).
  3. המקבל שומר את 4 ו-5 ומאשר אותם.
  4. pkt2 מגיע ל-timeout ← משדרים שוב רק את pkt2. המקבל מוסר את 2, 3, 4, 5 בבת אחת ושולח ack2.
מלכודת מבחן

הדילמה של SR: מספרי רצף 0, 1, 2, 3 ‏(k = 2) וחלון N = 3. מקרה A: השולח שולח 0, 1, 2, כל ה-ACKs אובדים, והוא משדר שוב את pkt0. מקרה B: כל ה-ACKs מגיעים, השולח שולח 3, 0 (חדש), ו-pkt3 אובד. בשני המקרים המקבל, שהחלון שלו עכשיו 3, 0, 1, רואה "pkt0" ומקבל אותו כמידע חדש. במקרה A זו כפילות ישנה ← נמסר מידע שגוי. הכלל: N ≤ 2k−1 (החלון לכל היותר חצי ממרחב מספרי הרצף).

10חזרה

שני לקוחות שולחים datagrams של UDP לאותו פורט בשרת. כמה sockets יש בשרת?

אחד. ב-TCP היו שני sockets של חיבור (4-tuples שונים).

איזו בעיה פותרת כל אחת מ-rdt 2.0, ‏2.1 ו-3.0?

2.0: שגיאות ביטים (checksum + ‏ACK/NAK + שידור חוזר). 2.1: ‏ACK/NAK משובש (מספרי רצף של ביט אחד לזיהוי כפילויות). 3.0: אובדן (timeout ושידור חוזר).

מה הניצולת של stop-and-wait עם L/R = 1 ms ו-RTT = 9 ms?

1 / (9 + 1) = 0.1.

למספרי הרצף יש 3 ביטים. מה החלון המרבי ב-GBN וב-SR?

GBN: ‏23 − 1 = 7. ‏SR: ‏22 = 4.

למה מקבל ב-SR שולח שוב ACK על חבילות מתחת לחלון שלו?

ייתכן שה-ACK הקודם אבד; בלי ACK חדש החלון של השולח לא יזוז אף פעם.
