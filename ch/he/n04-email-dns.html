דואר אלקטרוני ו-DNS

הרצאה 4 מכסה שני פרוטוקולי אפליקציה שכל השאר תלוי בהם. דואר אלקטרוני מראה פרוטוקול push ‏(SMTP) לצד פרוטוקולי pull ‏(IMAP, ‏POP3) ושיחת פקודה/תשובה מבוססת טקסט. DNS מראה איך מסד נתונים מבוזר והיררכי עונה על מיליארדי חיפושי שמות ביום, רובם מתוך מטמונים.

1דואר אלקטרוני: שלושה רכיבים עיקריים

רכיבתפקיד
User agent (קורא מייל)כתיבה, עריכה וקריאה של הודעות: Outlook, ‏Apple Mail, ‏Thunderbird, דף webmail. הודעות יוצאות ונכנסות נשמרות בשרת.
שרתי מיילתיבת דואר (mailbox) שומרת הודעות נכנסות לכל משתמש; תור הודעות (message queue) שומר הודעות יוצאות שמחכות להישלח.
SMTPSimple Mail Transfer Protocol ‏(RFC 5321): מעביר הודעות בין שרתי מייל. השרת השולח מתפקד כלקוח SMTP, והשרת המקבל כשרת SMTP.
אליס שולחת הודעה לבוב
  1. אליס כותבת הודעה ל-bob@someschool.edu ב-user agent שלה.
  2. ה-UA שלה שולח אותה לשרת המייל שלה ‏(submission, ‏SMTP בפורט 587); ההודעה נכנסת לתור ההודעות.
  3. השרת של אליס, כלקוח SMTP, מחפש ב-DNS את רשומת ה-MX של someschool.edu ופותח חיבור TCP לשרת של בוב בפורט 25.
  4. הוא שולח את ההודעה על החיבור בשיחת SMTP.
  5. השרת של בוב שם את ההודעה בתיבה של בוב.
  6. ה-UA של בוב קורא אותה בפרוטוקול pull: ‏IMAP או HTTP ‏(webmail).
לזכור

אין חיבור ישיר בין המחשב של אליס למחשב של בוב, ובדרך כלל גם אין שרתי מייל בדרך: השרת של אליס מדבר ישירות עם השרת של בוב. אם השרת של בוב לא זמין, ההודעה נשארת בתור של השרת של אליס ונשלחת שוב (בדרך כלל כל 30 דקות במשך כמה ימים).

2תכונות SMTP

  • משתמש ב-TCP להעברה אמינה של הודעות, פורט שרת 25.
  • שלושה שלבים בהעברה: handshaking (ברכה), העברת הודעות, סגירה.
  • אינטראקציה של פקודה/תשובה, כמו ב-HTTP: הפקודות הן טקסט ASCII, והתשובות הן קוד סטטוס ומשפט.
  • הודעות (header וגוף) חייבות להיות ב-ASCII של 7 ביט. קבצים מצורפים בינאריים מקודדים ל-ASCII בעזרת MIME ‏(base64).
  • חיבורים persistent: כמה הודעות לאותו שרת עוברות על חיבור TCP אחד.
  • סוף הודעה מסומן ב-CRLF.CRLF (שורה עם נקודה בודדת).

3שיחת SMTP מלאה

S = שרת (crepes.fr שמקבל), C = לקוח (hamburger.edu ששולח). לפני זה, handshake של TCP לפורט 25 לקח RTT אחד.

S: 220 hamburger.edu                         ← greeting
C: HELO crepes.fr                             ← handshake (EHLO for extended SMTP)
S: 250 Hello crepes.fr, pleased to meet you
C: MAIL FROM: <alice@crepes.fr>              ← envelope sender
S: 250 alice@crepes.fr... Sender ok
C: RCPT TO: <bob@hamburger.edu>              ← envelope recipient (repeat for each)
S: 250 bob@hamburger.edu ... Recipient ok
C: DATA
S: 354 Enter mail, end with "." on a line by itself
C: Do you like ketchup?
C: How about pickles?
C: .                                           ← end of message (CRLF.CRLF)
S: 250 Message accepted for delivery
C: QUIT
S: 221 hamburger.edu closing connection

אפשר לנסות במעבדה: telnet <servername> 25 ולהקליד את הפקודות. (שרתים אמיתיים דורשים היום STARTTLS ואימות לשליחה, ומסנני ספאם דוחים את רוב המיילים שמוקלדים ידנית.)

מלכודת מבחן

ה-envelope ‏(MAIL FROM / RCPT TO) הוא מה שהשרתים מנתבים לפיו; השורות From: / To: בתוך DATA הן רק טקסט שהמשתמש רואה. שום דבר ב-SMTP הבסיסי לא בודק שהם תואמים, ובגלל זה זיוף עובד ובגלל זה קיימים SPF, ‏DKIM ו-DMARC (פרק 08 בקורס האבטחה).

4מבנה הודעת מייל (RFC 5322) ו-MIME

RFC 5321 ‏(SMTP) מגדיר איך להעביר הודעה; RFC 5322 מגדיר את ההודעה עצמה: שורות header, שורה ריקה, ואז הגוף (רק ASCII).

From: alice@crepes.fr
To: bob@hamburger.edu
Subject: Searching for the meaning of life.
MIME-Version: 1.0
Content-Type: multipart/mixed; boundary="XYZ"

--XYZ
Content-Type: text/plain; charset=UTF-8

Hi Bob, see the picture.
--XYZ
Content-Type: image/jpeg
Content-Transfer-Encoding: base64

/9j/4AAQSkZJRgABAQEASABIAAD...
--XYZ--

MIME ‏(Multipurpose Internet Mail Extensions) מוסיף headers שמצהירים על סוג התוכן ועל הקידוד, כדי שמידע בינארי (תמונות, PDF) וטקסט שאינו באנגלית יוכלו לעבור בתוך הודעת ASCII של 7 ביט. ‏Base64 הופך כל 3 בתים ל-4 תווי ASCII (גדול ב-33%).

5פרוטוקולי גישה לדואר: IMAP, ‏POP3, ‏HTTP

SMTP הוא פרוטוקול push, ולכן המקבל לא יכול להשתמש בו כדי למשוך דואר מהשרת שלו. בשלב האחרון צריך פרוטוקול pull.

פרוטוקולפורטהתנהגות

POP3110 (995 TLS)שלב הרשאה (user, ‏pass), ואז שלב טרנזקציות (list, ‏retr, ‏dele, ‏quit). מצב "הורד ומחק" מוחק את הדואר מהשרת, כך שמכשיר שני לא רואה כלום; "הורד והשאר" משאיר עותקים. חסר מצב בין sessions.

6DNS: מה הוא מספק ולמה הוא מבוזר

אנשים משתמשים בשמות (www.yahoo.com); נתבים משתמשים בכתובות IP של 32 ביט. ה-Domain Name System ממפה ביניהם. הוא מסד נתונים מבוזר שממומש בהיררכיה של הרבה שרתי שמות, וגם פרוטוקול שכבת אפליקציה שבו מחשבים ושרתים שואלים אותו. הוא רץ מעל UDP פורט 53 ‏(TCP 53 לתשובות גדולות ול-zone transfers).

שירותמשמעות
תרגום שם ל-IPהתפקיד העיקרי (רשומות A / AAAA)
כינויים למחשביםשם קנוני עם כינויים נוחים יותר (CNAME)
כינויים לשרתי מייל@company.com ← שרת המייל בפועל (MX)
פיזור עומסהרבה כתובות IP לשם אחד; DNS מסובב את הסדר (שרתי web משוכפלים, CDN)
למה

למה לא שרת DNS מרכזי אחד? הוא היה נקודת כשל יחידה, היה צריך לשאת את כל נפח השאילתות בעולם (Akamai לבדה רואה טריליוני שאילתות ביום), היה רחוק מרוב המשתמשים, ולא היה אפשר לתחזק אותו. "זה לא סקלבילי".

8פענוח איטרטיבי מול רקורסיבי

המחשב cis.poly.edu רוצה את ה-IP של gaia.cs.umass.edu. הוא תמיד שואל את שרת ה-DNS המקומי שלו (השאילתה הראשונה רקורסיבית: "תביא לי את התשובה").

שאילתה איטרטיבית (המקרה הרגיל)

השרת המקומי שואל את ה-root ← ה-root עונה "לא יודע, תשאל את ה-TLD של ‎.edu בכתובת הזו" (referral) ← השרת המקומי שואל את ה-TLD ← referral לשרת המוסמך של umass.edu ← השרת המקומי שואל אותו ומקבל את רשומת ה-A.

8 הודעות: מחשב↔מקומי (2) + מקומי↔root ‏(2) + מקומי↔TLD ‏(2) + מקומי↔מוסמך (2). העומס נשאר על השרת המקומי.

שאילתה רקורסיבית

כל שרת שואל את הבא בשם הקודם: מקומי ← root ← TLD ← מוסמך, והתשובה חוזרת באותה שרשרת.

גם 8 הודעות, אבל זה מטיל עומס כבד על הרמות העליונות, ולכן שרתי root ו-TLD לא עושים את זה בפועל.

מטמון ו-TTL

כששרת כלשהו לומד מיפוי, הוא שומר אותו במטמון למשך ה-TTL של הרשומה. כתובות שרתי ה-TLD נשמרות בדרך כלל במטמון של השרתים המקומיים, ולכן כמעט לא פונים ל-root. רשומות במטמון יכולות להיות לא עדכניות: אם מחשב משנה IP, העולם עשוי לא לדעת עד שכל ה-TTL פגים ("תרגום שם לכתובת ב-best effort").

תזמון DNS + HTTP (קלאסי)

נתון

  • מטמון ה-DNS המקומי ריק. פענוח השם דורש n שרתי DNS עם RTT1…RTTn. ‏RTT0 לשרת ה-web; הדף הוא אובייקט קטן אחד.

פתרון

  1. זמן מהלחיצה לדף = (RTT1 + … + RTTn) + 2·RTT0
  2. בלי מטמון בכלל, כל אחת מ-3 הרמות (root, ‏TLD, מוסמך) עולה שאילתה: פי 3 מזמן שאילתה בודדת מעל ה-RTT לשרת המקומי.
  3. ביקור שני בתוך ה-TTL מדלג על DNS לגמרי.

13חזרה

למה SMTP נקרא פרוטוקול push, ובמה בוב משתמש כדי לקרוא את הדואר שלו?

השולח יוזם את החיבור ודוחף את ההודעה לשרת המקבל. בוב מושך אותה מהשרת שלו עם IMAP, ‏POP3 או HTTP.

איזו רשומה השרת של אליס מחפש כדי למסור ל-@someschool.edu?

את רשומת ה-MX של someschool.edu, ואז את רשומת ה-A של שרת המייל שהיא מציינת.

בפענוח איטרטיבי, מי עושה את העבודה?

שרת ה-DNS המקומי: הוא שולח כל שאילתה בעצמו ועוקב אחרי ה-referrals מה-root ל-TLD ולמוסמך.

מה קורה לרשומה במטמון אחרי שה-TTL שלה נגמר?

היא נזרקת, והחיפוש הבא הולך שוב להיררכיה.

למה DNS משתמש ב-UDP?

השאילתות קטנות וצריכות להיות מהירות: בלי RTT של handshake ובלי מצב חיבור בשרתים עמוסים. הלקוח פשוט מנסה שוב באובדן; ‏TCP משמש כשהתשובה גדולה מדי (דגל TC) או ל-zone transfers.
