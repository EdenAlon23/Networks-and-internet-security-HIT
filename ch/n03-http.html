Application layer and HTTP

Lecture 3 starts the top-down tour at the layer we use every day. First the principles every network application shares (architectures, processes and sockets, what an app needs from transport), then HTTP in full: message format, the RTT arithmetic of persistent and non-persistent connections, cookies, caches, and how HTTP/2 and HTTP/3 fix head-of-line blocking.

1Application architectures

Network applications run only on end systems; the network core does not run application code. That is what makes fast deployment possible: you write a program for two hosts, not for every router.

Client-server

Server: always-on host, permanent IP address, usually in a data center for scaling.

Clients: talk to the server, may be intermittently connected, may have dynamic IPs, do not talk directly to each other.

Examples: HTTP, IMAP, FTP.

Peer-to-peer (P2P)

No always-on server; arbitrary end systems communicate directly.

Self-scalability: new peers bring new service capacity as well as new demand.

Peers are intermittently connected and change IPs, so management is complex. Example: BitTorrent (chapter N05).

2Processes, sockets and addressing

A process is a program running on a host. Processes on different hosts communicate by exchanging messages. In every session one side is the client process (initiates) and the other the server process (waits to be contacted); P2P apps have both.

A process sends and receives messages through a socket, the door between the application and the transport layer. The app controls everything above the door; the OS controls transport and below.

To address a process you need both the host's 32-bit IP address and a 16-bit port number, because many processes run on one host. Well-known ports: HTTP 80, HTTPS 443, SMTP 25, DNS 53, IMAP 143.

An application-layer protocol defines: the message types (request, response), message syntax (fields and how they are delimited), semantics (meaning of each field), and rules for when and how to send and respond. Open protocols are defined in RFCs (HTTP, SMTP); proprietary ones are not (Skype, Zoom).

TCP service

Reliable in-order byte stream, flow control (never overwhelm the receiver), congestion control (throttle when the network is overloaded), connection-oriented (handshake first).

Does not provide: timing, minimum throughput guarantee, security.

UDP service

Unreliable, unordered datagrams. No connection setup, no flow or congestion control, no guarantees at all.

Why use it? No handshake delay, no connection state, small 8-byte header, and the app controls exactly when data is sent.

Security: TLS

Plain TCP and UDP sockets send cleartext, passwords included. TLS adds encryption, integrity and server authentication on top of TCP, implemented as a library in the application (HTTPS = HTTP over TLS).

Details in the security course, chapter 07.

4The Web and HTTP

A web page is a base HTML file plus several referenced objects (images, scripts, stylesheets), each addressable by a URL: www.someschool.edu/someDept/pic.gif = host name + path name.

HTTP (HyperText Transfer Protocol) is the web's client-server protocol. The client (browser) sends requests; the server sends objects in responses. It runs over TCP port 80 (HTTPS: 443): the client opens a TCP connection, they exchange HTTP messages, the connection is closed.

HTTP is stateless: the server keeps no information about past client requests. Protocols that keep state are complex (state must be kept consistent if a client or server crashes). State, when needed, is added with cookies.

5Persistent vs non-persistent HTTP: the RTT arithmetic

RTT (round-trip time): the time for a small packet to go from client to server and back. Fetching one object over a new TCP connection costs: 1 RTT to set up TCP (SYN, SYN-ACK), 1 RTT for the HTTP request and the first bytes of the response, plus the object's transmission time.

Non-persistent response time per object = 2·RTT + file transmission time

A page with 10 small images

Given

  • RTT = 20 ms to the server, transmission negligible. The base HTML references 10 images on the same server. DNS already cached.

Solution

  1. Non-persistent, serial: 2·20 + 10·2·20 = 440 ms
  2. Non-persistent, 5 parallel: 40 + ⌈10/5⌉·40 = 120 ms
  3. Persistent, no pipelining: 40 + 10·20 = 240 ms
  4. Persistent with pipelining: 40 + 20 = 60 ms
  5. If the DNS lookup were not cached and took RTT1 + … + RTTn to resolve, add that once at the start.
Exam trap

Count connections by host name, not by IP. Two URLs on different host names that resolve to the same IP still need two persistent connections in HTTP/1.1, because the browser keeps its connection pool per host (origin).

6HTTP message format

HTTP/1.x messages are human-readable ASCII. Each line ends with carriage return + line feed (\r\n), and an empty line separates the headers from the body.

Request

GET /index.html HTTP/1.1\r\n             ← request line: method, URL path, version
Host: www-net.cs.umass.edu\r\n            ← header lines
User-Agent: Firefox/3.6.10\r\n
Accept: text/html,application/xhtml+xml\r\n
Accept-Language: en-us,en;q=0.5\r\n
Accept-Encoding: gzip,deflate\r\n
Connection: keep-alive\r\n
\r\n                                       ← blank line = end of headers
(body: empty for GET; form data for POST)

Response

HTTP/1.1 200 OK\r\n                         ← status line: version, code, phrase
Date: Tue, 08 Sep 2020 00:53:20 GMT\r\n
Server: Apache/2.4.6 (CentOS)\r\n
Last-Modified: Tue, 01 Mar 2016 18:57:50 GMT\r\n
ETag: "a5b-52d015789ee9e"\r\n
Accept-Ranges: bytes\r\n
Content-Length: 2651\r\n
Content-Type: text/html; charset=UTF-8\r\n
\r\n
<html>... 2651 bytes of data ...

You can type this by hand: telnet gaia.cs.umass.edu 80 (or nc), then type the request lines and an empty line. This is the best way to see that HTTP is just text over a TCP connection. With curl -v http://example.com/ you see the same exchange.

8Cookies: keeping state over a stateless protocol

Four components: (1) a Set-Cookie: header in an HTTP response, (2) a Cookie: header in the next HTTP requests, (3) a cookie file kept on the user's host and managed by the browser, (4) a back-end database at the web site.

Step by step
  1. Susan visits amazon.com for the first time. The request carries no cookie for this site.
  2. The server creates ID 1678 and a database entry, and replies with Set-Cookie: 1678.
  3. The browser stores amazon 1678 in its cookie file and sends Cookie: 1678 in every later request to that site.
  4. The server performs a cookie-specific action (shopping cart, "recommended for you", stay logged in). A week later the same cookie is still sent.

Uses: authorization, shopping carts, recommendations, user session state. Privacy: cookies let sites learn a lot about you. Third-party cookies (set by an ad or tracker embedded in many sites, not the site you visit) let one company follow you across sites. Browsers now block many of them by default, and the GDPR treats cookie identifiers as personal data.

9Web caches (proxy servers)

A web cache satisfies client requests without involving the origin server. The browser is configured to send all requests to the cache; if the object is in the cache, it is returned immediately; otherwise the cache fetches it from the origin, stores a copy, and returns it. The cache is both a server (to the client) and a client (to the origin). It is usually installed by the ISP or the institution.

Why: shorter response time (the cache is closer), less traffic on the institution's access link, and it lets "poor" content providers deliver content effectively.

Caching example: upgrade the link or install a cache?

Given

  • Access link 1.54 Mbps; LAN 1 Gbps; RTT from the institution router to any origin server: 2 s
  • Objects of 100 kbit; browsers request 15 objects/s on average → 1.5 Mbps of data

Solution

  1. Access link utilization = 1.5 / 1.54 = 0.97 → queueing delays of minutes. Total delay ≈ Internet delay + minutes + μs.
  2. Option 1, buy a 154 Mbps link: utilization 0.0097, total ≈ 2 s + ms + μs. Expensive.
  3. Option 2, install a cache with hit rate 0.4: only 60% of requests cross the link → 0.6 × 1.5 = 0.9 Mbps, utilization 0.9 / 1.54 = 0.58 → small delay.
  4. Average delay = 0.6 × (≈2.01 s from origin) + 0.4 × (≈ms from cache) ≈ 1.2 s. Lower than with the fast link, and cheap.

10Conditional GET

Goal: don't send the object if the cache already has an up-to-date copy. The cache puts the date of its copy in the request; the server answers with no body if nothing changed.

cache → server   GET /fruit/kiwi.gif HTTP/1.1
                  Host: www.exotiquecuisine.com
                  If-Modified-Since: Wed, 9 Sep 2015 09:23:24

server → cache   HTTP/1.1 304 Not Modified          (no body: saves bandwidth)
          or     HTTP/1.1 200 OK  + the new object  (it did change)

ETag + If-None-Match does the same with a version identifier instead of a date. Cache-Control: max-age=3600 tells caches the object is fresh for an hour, so they need not ask at all during that time.

11HTTP/2 and HTTP/3

HTTP/1.1 serves requests in order, first-come-first-served (FCFS) on a connection. A large object (a video) at the head of the line makes small objects behind it wait: head-of-line (HOL) blocking. Loss recovery (TCP retransmission) also stalls everything behind the lost segment.

VersionKey changes
HTTP/1.0 (1996)Non-persistent by default; one object per TCP connection
HTTP/1.1 (1997)Persistent connections by default, pipelining (rarely used), mandatory Host: header (virtual hosting), chunked transfer, better caching
HTTP/2 (2015)Binary framing: objects are split into frames and frames of different objects are interleaved on one TCP connection, so small objects are not stuck behind big ones. Client-specified priorities, server push of objects the client has not requested yet, header compression (HPACK).
HTTP/3 (2022)Runs over QUIC, which runs over UDP. QUIC adds reliability, congestion control and built-in TLS 1.3 per stream at the application layer, so a lost packet only stalls its own stream (no HOL blocking across streams), and connection + security setup takes 1 RTT (0-RTT on resume).
Why

Why did HTTP/3 move to UDP? TCP is implemented in the OS kernel and in middleboxes, so changing it takes a decade. Building the new transport logic in user space on top of UDP lets browsers and servers deploy it immediately.

12Review

Why do you need both an IP address and a port to reach a process?

The IP identifies the host; many processes run on it, so the port identifies the socket of the right process.

Time to fetch one object over non-persistent HTTP?

2·RTT + transmission time: one RTT for the TCP handshake, one for request/response.

What does 304 mean, and when is it sent?

Not Modified: the answer to a conditional GET when the cached copy is still current. It has no body.

How does a stateless server remember your cart?

Set-Cookie gives you an ID; your browser returns it in the Cookie header and the server looks the ID up in its database.

What problem does HTTP/2 solve, and what does HTTP/3 add?

HTTP/2 interleaves frames to avoid HOL blocking between objects; HTTP/3 (QUIC over UDP) also avoids HOL blocking caused by TCP loss recovery and merges the transport and TLS handshakes.
