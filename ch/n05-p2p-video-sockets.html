1File distribution time: client-server vs P2P

Question: how much time does it take to distribute a file of F bits from one server to N peers? Notation: us = server upload rate, ui = peer i upload rate, di = peer i download rate, dmin = the slowest peer's download rate. Assume the core has plenty of bandwidth (only access links matter).

Client-server

The server must upload N copies: N·F / us. The slowest client needs F / dmin to download.

Dc-s ≥ max{ N·F/us , F/dmin }

Grows linearly in N.

Peer-to-peer

The server must upload at least one copy: F / us. The slowest peer needs F / dmin. In total N·F bits must be downloaded, and the maximum total upload rate is us + Σui.

DP2P ≥ max{ F/us , F/dmin , N·F/(us + Σui) }

The last term grows with N in the numerator, but so does the denominator: each peer brings upload capacity.

Numbers

Given

  • F = 15 Gbit, us = 30 Mbps, dmin = di = 2 Mbps, every peer uploads u = 300 kbps; N = 10, 100, 1,000

Solution

  1. F/dmin = 15·109 / 2·106 = 7,500 s; F/us = 500 s
  2. Client-server, N = 1,000: N·F/us = 500,000 s ≈ 139 hours. Doubles if N doubles.
  3. P2P, N = 1,000: N·F/(us + N·u) = 1.5·1013 / (3·107 + 3·108) ≈ 45,455 s; max with 7,500 and 500 → ≈ 12.6 hours.
  4. As N → ∞ the P2P term tends to F/u = 15·109/3·105 = 50,000 s: bounded, while client-server keeps growing.
Exam trap

Always take the maximum of the terms (it is a lower bound: the slowest constraint wins), and convert units first: F is often given in Gbits or GBytes, rates in Mbps.

2BitTorrent

  • The file is divided into chunks of 256 KB. The set of peers exchanging chunks of one file is a torrent.
  • A tracker keeps track of the peers in the torrent. A joining peer registers with the tracker, gets a list of peers, and connects to a subset of them ("neighbours"). Many clients also use a DHT instead of a tracker.
  • A new peer has no chunks; it accumulates them over time while uploading the ones it has. Once it has the whole file it may leave (selfishly) or stay as a seeder. Peers come and go: churn.

Requesting chunks: rarest first

Periodically, Alice asks each neighbour for its list of chunks, then requests the missing chunks that are rarest among her neighbours. Rare chunks are thus replicated quickly, so the file survives churn.

Sending chunks: tit-for-tat

Alice sends to the 4 peers currently sending to her at the highest rate; the others are choked. The top 4 is re-evaluated every 10 s.

Every 30 s she optimistically unchokes one random peer. That peer may become one of Bob's top 4, and newcomers with nothing to trade still get a start.

Why

Tit-for-tat makes cooperation the best strategy: the more you upload, the better trading partners you find and the faster you download. Free-riders get only the occasional optimistic unchoke.

3Video: why it is different

Streaming video is the largest consumer of Internet bandwidth (Netflix, YouTube and Amazon Prime were about 80% of residential ISP traffic around 2020). A video is a sequence of images displayed at a constant rate, e.g. 24–30 images per second, and each image is an array of pixels. Raw video is huge, so it is compressed using redundancy:

Spatial (within an image)

Instead of sending N values of the same colour, send only two values: the colour value and the number of repeated values N (run-length coding).

Temporal (between images)

Instead of sending the complete frame i+1, send only the differences from frame i.

CBR vs VBR

CBR (constant bit rate): the encoding rate is fixed. VBR (variable): the rate changes as the amount of spatial/temporal coding changes. Examples: MPEG-1 (CD-ROM) 1.5 Mbps, MPEG-2 (DVD) 3–6 Mbps, MPEG-4 / H.264 (Internet) 64 kbps – 12 Mbps.

4Streaming stored video: the client buffer

The server stores the video; the client plays it while the rest is still downloading. Challenges: the server-to-client bandwidth varies over time (congestion at home, in the access network, in the core, at the server), and packet loss and delay vary too.

What happens in time
  1. The video is recorded (e.g. 30 frames/s) and sent; network delay is variable (jitter), so frames arrive unevenly.
  2. The client stores the arriving data in a playout buffer and waits an initial playout delay before starting.
  3. Playback then runs at the constant rate; the buffer absorbs the variation in arrival. If the buffer empties, playback freezes (the spinning wheel) until it fills again.
  4. Larger initial delay = fewer stalls but a longer wait before the video starts. Interactivity (pause, skip ahead) also matters.
Remember

If the average fill rate x is smaller than the playout rate r, the buffer eventually empties no matter how big the initial delay; if x > r, a moderate initial delay prevents stalls.

5DASH: Dynamic Adaptive Streaming over HTTP

Server side

Divides the video file into multiple chunks (a few seconds each).

Each chunk is encoded at several different rates (e.g. 300 kbps, 1 Mbps, 3 Mbps, 8 Mbps); each encoding is stored in a separate file.

Files are replicated on many CDN nodes.

A manifest file provides the URLs for the different chunks and rates.

Client side ("intelligence at the client")

Periodically estimates the server-to-client bandwidth.

Consulting the manifest, requests one chunk at a time with plain HTTP GET.

Chooses the maximum coding rate sustainable given the current bandwidth, and can choose a different rate at different times and different servers.

Decides when to request (so the buffer neither starves nor overflows), what rate, and where (a nearby or high-bandwidth server).

Why

Why over HTTP? HTTP over TCP passes through firewalls and NATs everywhere, uses ordinary web caches and CDNs, and the server stays stateless. Lost packets are retransmitted by TCP, and the client buffer hides the delay.

6Content distribution networks (CDNs)

How do you stream to hundreds of thousands of simultaneous users? Option 1: a single, large "mega-server": a single point of failure, a point of network congestion, a long path to distant clients, and multiple copies of the same video sent over the same outgoing link. It doesn't scale. Option 2: store multiple copies of the videos at many geographically distributed sites: a CDN.

Netflix (an over-the-top service)
  1. Bob browses Netflix (pages served from Netflix's own servers in the cloud) and picks an episode.
  2. Netflix returns a manifest listing the CDN servers and URLs of the chunks at each rate.
  3. Bob's client picks a server (often in his own ISP: Netflix Open Connect boxes) and requests chunks with DASH.
  4. If the path to that server gets congested, the client switches rate or server.

This is OTT (over the top): the service is built by the content provider on top of the best-effort Internet, with all the intelligence at the edges (where to store content, which server to choose, which rate), without help from the network core. How does the client reach the nearby CDN server? Often by DNS: the CDN's authoritative DNS server returns the IP of a server close to the client's local DNS server (DNS redirection, see N04).

7Socket programming

Goal: build client/server applications that communicate using sockets. A socket is the door between the application process and the end-to-end transport protocol. Two socket types for two transport services: UDP (unreliable datagram) and TCP (reliable, byte-stream oriented).

The lecture's example app: (1) the client reads a line of characters from the keyboard and sends it to the server, (2) the server converts it to uppercase, (3) the server sends the modified data back, (4) the client displays it.

8UDP client and server in Python

UDPClient.py

from socket import *
serverName = 'hostname'
serverPort = 12000
clientSocket = socket(AF_INET, SOCK_DGRAM)          # IPv4 + UDP
message = input('Input lowercase sentence:')
clientSocket.sendto(message.encode(), (serverName, serverPort))  # dest attached to EVERY datagram
modifiedMessage, serverAddress = clientSocket.recvfrom(2048)    # reply + who sent it
print(modifiedMessage.decode())
clientSocket.close()

UDPServer.py

from socket import *
serverPort = 12000
serverSocket = socket(AF_INET, SOCK_DGRAM)
serverSocket.bind(('', serverPort))                 # listen on port 12000, all interfaces
print('The server is ready to receive')
while True:
    message, clientAddress = serverSocket.recvfrom(2048)   # clientAddress = (IP, port)
    modifiedMessage = message.decode().upper()
    serverSocket.sendto(modifiedMessage.encode(), clientAddress)

Run the server first, then the client in a second window (use localhost as serverName to test on one machine). Notice that the server never "accepts": the first datagram simply arrives, and the server learns the client's address from recvfrom. In Wireshark, filter with udp.port == 12000: you will see exactly two datagrams, with no handshake.

9TCP client and server in Python

TCPClient.py

from socket import *
serverName = 'servername'
serverPort = 12000
clientSocket = socket(AF_INET, SOCK_STREAM)         # IPv4 + TCP
clientSocket.connect((serverName, serverPort))      # 3-way handshake happens here
sentence = input('Input lowercase sentence:')
clientSocket.send(sentence.encode())                # no address: the connection knows it
modifiedSentence = clientSocket.recv(1024)
print('From Server:', modifiedSentence.decode())
clientSocket.close()                                # FIN

TCPServer.py

from socket import *
serverPort = 12000
serverSocket = socket(AF_INET, SOCK_STREAM)
serverSocket.bind(('', serverPort))
serverSocket.listen(1)                              # welcoming socket, backlog 1
print('The server is ready to receive')
while True:
    connectionSocket, addr = serverSocket.accept()  # NEW socket for this client
    sentence = connectionSocket.recv(1024).decode()
    capitalizedSentence = sentence.upper()
    connectionSocket.send(capitalizedSentence.encode())
    connectionSocket.close()                        # close this client, keep listening
What happens on the wire
  1. listen(): the server's welcoming socket waits on port 12000.
  2. connect(): the client OS sends SYN, gets SYN-ACK, replies ACK (1.5 RTT, the client can send after 1 RTT).
  3. accept() returns a new socket bound to this specific client (its 4-tuple). The welcoming socket keeps listening for other clients.
  4. send()/recv() move bytes; TCP handles ACKs, retransmissions and ordering underneath.
  5. close() sends FIN; the other side ACKs and closes its half too.
In practice

This server handles one client at a time (the loop blocks in recv). Real servers use a thread or process per connection, or an event loop (select/epoll, asyncio). And since TCP is a byte stream, one send() may arrive as several recv()s: real protocols add their own message framing (a length field or a delimiter, like HTTP's CRLF and Content-Length).

10Review

Why does P2P distribution time stay bounded as N grows?

Every new peer adds upload capacity ui, so the aggregate upload rate grows with N along with the demand.

What does a BitTorrent peer request first, and whom does it send to?

The rarest chunks among its neighbours; it sends to the top 4 peers that send to it fastest (every 10 s), plus one optimistic unchoke every 30 s.

In DASH, who decides the bitrate?

The client, chunk by chunk, using its bandwidth estimate and buffer level and the manifest.

Why does a TCP server need two kinds of sockets?

The welcoming socket accepts new connections; each accepted connection gets its own socket identified by the full 4-tuple.

Two UDP clients send to server port 12000. How many sockets does the server use?

One: UDP demultiplexes only on destination IP and port.
