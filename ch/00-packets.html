1Layers, PDUs and addresses

Each layer adds its own header in front of the data it receives from above (encapsulation), and the receiver removes them in reverse order (decapsulation). Every header answers one question for one device: the Ethernet header tells the next switch or router which machine on this link, the IP header tells routers which machine on the Internet, the TCP/UDP header tells the destination OS which process.

Why two kinds of address

MAC addresses are flat (no hierarchy), so they only work inside one link. IP addresses are hierarchical (network prefix + host), so routers can summarize millions of hosts into one routing entry. Every hop therefore uses a new frame (new MACs) around the same packet (same IPs).

Abuse map

Almost every attack in this course forges one field of one layer: MAC flooding forges L2 source MACs, ARP poisoning forges the L2→L3 mapping, IP spoofing forges the L3 source, scans play with L4 flags, DNS poisoning forges an L7 answer. Knowing who reads which field tells you who can be fooled.

The MAC address

48 bits written as 6 hex bytes, e.g. 3c:22:fb:12:a4:01. The first 3 bytes are the OUI (vendor: 3c:22:fb = Apple), which is how scanners print the vendor name. Bit 0 of the first byte = group (multicast/broadcast); bit 1 = locally administered (random MACs on phones set it).

What a switch does with each frame

  1. Learn: write source MAC → incoming port in the CAM table (with an aging timer, about 300 s).
  2. Forward: look up the destination MAC. Known → send out of that one port. Unknown or broadcast → flood to all ports except the incoming one.
  3. Filter: if the destination is on the same port it came from, drop it.
Attacks at this layer
  • MAC flooding (macof): fill the CAM table so the switch floods everything (see the animation in chapter 04).
  • MAC spoofing: change your MAC to an allowed one to bypass MAC filtering or captive portals.
  • Broadcast storms: loops without STP multiply broadcasts until the network stops.
Defenses

Port security (max MACs per port, sticky MACs), 802.1X authentication per port, VLAN segmentation, storm control, BPDU guard.

ARP packet: 28 bytes, carried directly in Ethernet with EtherType 0x0806. Red = the fields an attacker forges.

Exact steps
  1. Host A needs to send to 192.168.1.20. It checks the routing table: same subnet → the next hop is .20 itself (otherwise the next hop is the gateway, and A resolves the gateway IP).
  2. A looks in its ARP cache (arp -a / ip neigh). Miss.
  3. A broadcasts a Request: Ethernet dst ff:ff:ff:ff:ff:ff; ARP opcode 1, sender = A's MAC/IP, target MAC = 00:00:00:00:00:00, target IP = .20. The IP packet waits in a queue.
  4. Every host receives it. Only the owner of .20 answers; it also caches A's mapping from the sender fields.
  5. B sends a unicast Reply: opcode 2, sender = B's MAC/IP, target = A.
  6. A caches .20 → BB (Linux: entries become STALE after about 30 s and are re-verified; Windows: about 15–45 s reachable time) and sends the queued packet.

Gratuitous ARP: a host announces its own mapping unasked (sender IP = target IP), e.g. after boot or failover, so others update their caches. It is legitimate, and it is exactly the mechanism ARP poisoning abuses.

Why ARP is so easy to abuse

ARP has no authentication and is stateless: most stacks accept a Reply they never requested and overwrite the cache. An attacker sends "192.168.1.1 is at MY MAC" to the victim and "192.168.1.10 is at MY MAC" to the gateway, and becomes the man in the middle (chapter 04).

Defenses

Dynamic ARP Inspection (the switch checks ARP replies against its DHCP-snooping binding table), static ARP entries for critical hosts, IDS alerts (arpwatch) on MAC changes, and above all encryption (TLS, SSH, IPsec) so a MITM gains nothing readable.

Why the receiver cannot trust Source IP

Routers forward based on the destination only. Nothing on the path checks that the source belongs to the sender, unless the edge network applies ingress filtering (BCP 38 / uRPF). For UDP and ICMP a forged source just works. For TCP, a spoofer never sees the SYN/ACK, so cannot complete a handshake (unless it can guess the server's ISN).

5Fragmentation and reassembly in detail

Every link has a maximum frame payload, the MTU (Ethernet 1500, PPPoE 1492, many VPN tunnels about 1400). When a router must forward a packet larger than the next link's MTU it has two choices: fragment it (if DF=0) or drop it and report back (if DF=1). IPv4 routers may fragment; in IPv6 only the sender may.

Fragmenting: exact algorithm (router or sender)
  1. Space for data per fragment = MTU − IP header length (1500 − 20 = 1480).
  2. Round down to a multiple of 8, because the offset field counts 8-byte blocks (1480 is already a multiple: 185 × 8).
  3. Copy the original header into each fragment. Keep Identification, Source, Destination and Protocol the same.
  4. Set Offset = (byte position of this fragment's data in the original payload) / 8.
  5. Set MF=1 on every fragment except the last; the last keeps the original MF (normally 0).
  6. Set Total Length of each fragment to its own header + data, and recompute each header checksum.
  7. Options marked "copy" are copied to every fragment; others go only in the first.

Reassembly at the destination: exact steps
  1. A packet arrives with MF=1 or Offset≠0 → it is a fragment.
  2. Find (or create) a reassembly buffer keyed by (Source IP, Destination IP, Protocol, Identification), and start a timer for it (RFC 791 suggests 15 s; Linux uses 30 s).
  3. Copy the fragment's data into the buffer at byte position Offset × 8. Record which ranges are filled.
  4. The fragment with MF=0 tells the total payload length = its Offset × 8 + its data length.
  5. When the total length is known and there are no holes, rebuild one IP header (Total Length = full size, MF=0, Offset=0) and pass the datagram to the protocol in the Protocol field.
  6. If the timer expires first: discard everything; if fragment 0 had arrived, send ICMP Time Exceeded, Code 1 (fragment reassembly time exceeded).

Why only at the destination? Fragments may take different paths, so no router is guaranteed to see them all, and reassembling at every hop would cost memory and time in the core of the network.

Why avoid fragmentation today? Losing one fragment loses the whole datagram (no retransmission at IP level), firewalls cannot see ports in fragments 2+, and reassembly costs memory. So TCP sets DF=1 and uses Path MTU Discovery: if a router answers ICMP Type 3 Code 4 with the next-hop MTU, the sender lowers its segment size (MSS). If a firewall blocks that ICMP, large packets silently vanish: a "PMTU black hole".

Fragmentation abuse
  • Teardrop: overlapping fragments that make old reassembly code compute a negative length (chapter 05).
  • Ping of Death: Offset × 8 + length > 65,535 overflows the buffer.
  • Tiny fragments (nmap -f, --mtu 8): the TCP flags land in fragment 2, so a filter that checks only the first fragment misses them.
  • Overlapping rewrite: a later fragment overwrites earlier bytes; if the IDS and the target resolve overlaps differently, they see different data (insertion/evasion).
  • Fragment flood: send only first fragments to exhaust reassembly buffers.
Defenses

Firewalls and IDSs that reassemble before inspecting ("virtual reassembly"), dropping fragments smaller than a minimum size (RFC 1858) or with overlaps (RFC 5722 forbids overlaps in IPv6), limiting reassembly memory and timeouts, and allowing ICMP Type 3 Code 4 through so PMTUD works.

Why the error carries the original header + 8 bytes

The 8 bytes cover the UDP header or the TCP ports and sequence number, so the sender can tell which socket the error belongs to. That is how traceroute matches each Time Exceeded to its probe, and also why scanners can read results from ICMP errors.

Filter ICMP, do not kill it

Allow Echo Reply, Type 3 (especially Code 4) and Type 11 back in for your own connections; rate-limit Echo Requests; drop Redirects and Echo to broadcast addresses. Blocking all ICMP breaks PMTUD and troubleshooting.

Handshake and sequence math
  1. Client → SYN, Seq = x (random ISN), options MSS/SACK/WScale.
  2. Server → SYN+ACK, Seq = y, Ack = x+1. Server keeps a half-open entry (SYN-RCVD) in the backlog.
  3. Client → ACK, Seq = x+1, Ack = y+1. Both ESTABLISHED.
  4. Data: each side's Seq advances by the number of payload bytes; Ack = the next byte expected. SYN and FIN each consume one number.
  5. Close: FIN → ACK, FIN → ACK (four segments), the closer waits in TIME-WAIT for 2×MSL.

Ports: the server listens on a well-known port (0–1023, e.g. 22, 25, 53, 80, 443); the client uses an ephemeral port (Linux 32768–60999, Windows 49152–65535). A connection is identified by the 4-tuple (src IP, src port, dst IP, dst port), which is what NAT and stateful firewalls track.

Window: flow control, how many more bytes the receiver can buffer. The initial window and the options order differ per OS, which passive fingerprinting (p0f) uses.

TCP abuse
  • Scans exploit the RFC response rules: open ports answer SYN with SYN/ACK, closed ports with RST, and stray FIN/Null/Xmas segments get RST only from closed ports (chapter 03).
  • SYN flood: half-open entries fill the backlog (chapter 05).
  • Session hijacking / RST injection: a packet with the right 4-tuple and a Seq inside the window is accepted. Random ISNs (RFC 6528) make blind guessing impractical; an on-path attacker (after ARP poisoning) can still do it.

UDP header: only 8 bytes.

No handshake, no sequence numbers, no retransmission, no connection state. The application does whatever reliability it needs. That makes it fast and ideal for DNS, DHCP, NTP, SNMP, VoIP/RTP, games, QUIC.

The checksum covers a pseudo-header (source IP, destination IP, protocol, length) too, so a packet delivered to the wrong IP is detected. In IPv4 it may be 0 (disabled); in IPv6 it is mandatory.

Why UDP is the reflection protocol

With no handshake, the server answers whatever source address the request claims. A spoofed 60-byte request that triggers a 3,000-byte answer turns servers into amplifiers aimed at the victim (DNS, NTP, SSDP, memcached; chapter 05). UDP scanning is slow for the same reason: an open port often says nothing at all.

Flags: QR (0 query, 1 response), AA (answer from an authoritative server), TC (truncated → retry over TCP), RD (client asks for recursion), RA (server offers recursion). A resolver that sets RA for anyone on the Internet is an open resolver, a ready-made amplifier.

DNS abuse
  • Cache poisoning: the only things binding an answer to a query are the 16-bit ID, the source port and the question. Guess them before the real answer arrives and the resolver caches your record (chapter 04).
  • Amplification: small spoofed ANY/DNSSEC queries, big answers (chapter 05).
  • Tunnelling / exfiltration: data encoded in subdomain labels passes most firewalls because DNS is always allowed.
Defenses

Source-port randomization, DNSSEC validation, closing open recursion, response rate limiting, restricting AXFR to secondaries (+TSIG), and monitoring for long or high-entropy query names.

DHCP is UDP on ports 67 (server) and 68 (client). Routers forward it between subnets with a relay agent (ip helper-address, adds option 82). Renewal happens at 50% of the lease (T1) by unicast to the same server.

DHCP abuse

Rogue DHCP: answer faster than the real server and hand out your own router and DNS (option 3 and 6) → MITM for every new client. Starvation: thousands of Discovers with random chaddr empty the pool, often as step one before running a rogue server.

Defenses

DHCP snooping (only trusted uplink ports may send Offer/Ack; rate-limit Discovers per port), which also builds the IP-MAC binding table that Dynamic ARP Inspection and IP Source Guard use.

11Full journey: typing http://example.com

Every packet, in order
  1. DHCP (at boot): the laptop gets 192.168.1.10/24, gateway 192.168.1.1, DNS 192.168.1.1.
  2. ARP for the gateway: "who has 192.168.1.1?" broadcast; reply with the router MAC. Cached.
  3. DNS: UDP 192.168.1.10:53124 → 192.168.1.1:53, ID 0x1a2b, "example.com A?". Ethernet dst = router MAC. The router's resolver recurses (root → .com → authoritative) and answers 93.184.216.34.
  4. TCP handshake: SYN to 93.184.216.34:80 from an ephemeral port, DF=1, TTL 64, MSS 1460. The home router NATs it: source becomes its public IP and a new port; TTL 63.
  5. Each Internet router: new frame, TTL−1, checksum recomputed, longest-prefix match. IPs and ports unchanged.
  6. SYN/ACK comes back; NAT maps it to 192.168.1.10:ephemeral; client sends ACK.
  7. HTTP: PSH,ACK carrying "GET / HTTP/1.1, Host: example.com". Server ACKs and sends "200 OK" in one or more segments (each ≤ MSS, so no IP fragmentation).
  8. The browser parses HTML, opens more connections for images/CSS (often to other names → more DNS).
  9. FIN/ACK exchange closes the connection (or it stays open with keep-alive).
With HTTPS

Same until step 7, but on port 443: a TLS handshake first (ClientHello with SNI = example.com in clear text, ServerHello, certificate, key exchange with ECDHE, Finished), then HTTP inside encrypted TLS records. An on-path observer still sees IPs, ports, packet sizes, timing, DNS queries (unless DoH) and the SNI.

Where an attacker can step in

Rogue DHCP (step 1), ARP poisoning (step 2), DNS spoofing (step 3), sniffing everything in clear text (step 7 over HTTP), TCP injection if on-path. Each later chapter takes one of these steps apart.
