1Why we need public keys

Problem 1: key distribution

To talk secretly you already need a shared secret. Chicken and egg. With n participants you need n(n−1)/2 symmetric keys.

Problem 2: no real authentication

With a shared key the receiver can forge a message and claim the sender sent it. No non-repudiation.

The solution: each party has two keys. Public (K+), anyone may know it; used to encrypt and to verify signatures. Private (K−), only the owner knows it; used to decrypt and to create signatures. "The most significant advance in 3,000 years of cryptography", based on number theory. It complements symmetric encryption, it does not replace it.

Requirements of a public-key algorithm

  1. Easy for B to generate a key pair.
  2. Easy for A to encrypt with B's public key.
  3. Easy for B to decrypt with the private key.
  4. Computationally infeasible to derive the private key from the public key.
  5. Infeasible to recover the message from the public key and the ciphertext.
  6. (Desirable) either key can encrypt and the other decrypts: K−(K+(m)) = m = K+(K−(m)).

2Three uses

Key exchange

Alice generates a random symmetric key (e.g. 56 bits for DES: B4 41 29 0B 1C F7 63), encrypts it with Bob's public key and sends it. Bob opens it with his private key. From here on they continue with fast symmetric encryption. This is hybrid encryption, and it is how TLS, PGP and S/MIME work.

Why hybrid

Public-key operations (modular exponentiation) are 100–1000× slower than the substitutions and XORs of symmetric ciphers, and the keys are longer (RSA 2048 bits vs AES 128). So public key is used only to exchange the session key and for signatures.

3RSA (Rivest, Shamir, Adleman · MIT 1977)

The most widely used scheme. Keys over 1000 bits. Security rests on the difficulty of factoring a large number that is the product of two primes. The patent expired in September 2000.

Key generation

  1. Choose two primes p, q.
  2. n = p·q, z = (p−1)(q−1).
  3. Choose e < n coprime to z (gcd(e, z) = 1).
  4. Compute d so that e·d mod z = 1.
  5. Public: {e, n}. Private: {d, n}. Discard p, q.

Encryption and decryption

c = me mod n
m = cd mod n

"Magic happens": (me)d = med ≡ m (mod n), because ed ≡ 1 (mod φ(n)) and Euler's theorem.

Small RSA calculator

Common exam question: how do you compute d?
Extended Euclid on (e, z). In the example: 160 = 22·7 + 6, 7 = 1·6 + 1 → 1 = 7 − 6 = 7 − (160 − 22·7) = 23·7 − 160. So d = 23.
Check: 887 mod 187 = 11, and 1123 mod 187 = 88.






4RSA security and attacks


Factoring
n is public. Whoever factors n = p·q computes z and then d. Time grows exponentially with the size of the number. RSA Challenges: RSA-250 (829 bits) was factored in 2020. Today at least 2048 bits is recommended.
Timing attack
Decryption time depends on the bits of d. Precise measurement reveals them. Defense: blinding (multiply by a random re before, divide by r after).
Power attack
The CPU's power consumption during decryption (mainly on smart cards) reveals the square and multiply operations, and therefore d.
Quantum computing
Shor's algorithm factors in polynomial time. Hence the move to post-quantum (NIST 2024: ML-KEM / Kyber, ML-DSA / Dilithium). Chrome and Cloudflare already use hybrid X25519+Kyber.
Practical attacks (beyond the slides)
Textbook RSA (no padding) is deterministic and vulnerable: same message = same ciphertext, and a small m with e=3 falls to a cube root. Hence OAEP.
Bleichenbacher (1998) / ROBOT (2017): a padding oracle on PKCS#1 v1.5 in TLS.
Weak keys: bad random generators produced keys sharing a prime; gcd of two n values factors both (2012). ROCA (2017): a bug in an Infineon library that allowed factoring keys of Estonian ID cards.
Other algorithms
DSS / DSA: signatures only (with SHA), not for encryption or key exchange. ECC: the same security with much smaller keys (256-bit ECC ≈ 3072-bit RSA). The 2015 lecture says "low confidence level and very complex"; today ECC (Curve25519, P-256) is the default in TLS 1.3, SSH and Signal.






5Hash functions


A function that takes input of any size and returns a fixed-length value h = H(M). Any small change in M must give a different h (avalanche effect). Used for message and file integrity.
#PropertyMeaningBrute-force cost (n bits)
1–3any input size, fixed output, easy to compute
4One-way (preimage resistance)given h, you cannot find M with H(M)=h2n
5Weak collision (second preimage)given M1, you cannot find M2 with the same hash. Prevents forgery2n

Why the Internet checksum is a bad cryptographic hash
It has some of the properties (fixed output, many-to-one), but it is very easy to find another message with the same checksum:
IOU1 00.9 9BOB → 49 4F 55 31 · 30 30 2E 39 · 39 42 D2 42 → B2 C1 D2 AC
IOU9 00.1 9BOB → 49 4F 55 39 · 30 30 2E 31 · 39 42 D2 42 → B2 C1 D2 AC
"I owe 100.99" became "I owe 900.19" with the same checksum, because a sum is order-insensitive: we added 8 in one byte and subtracted 8 in a parallel byte.

Hashes for passwords
A fast hash (MD5/SHA) alone is bad for passwords: a GPU computes billions per second, and rainbow tables cover common passwords. So: a unique salt per user + a deliberately slow function (bcrypt, scrypt, Argon2).






6The birthday attack


The birthday paradox: among 23 people, the chance someone shares Elvis's birthday ≈ 6%. But the chance that any two share a birthday ≈ 50%, because there are 23·22/2 = 253 pairs.
In general: with k tries and N possible values there are about k²/2N colliding pairs, so a collision is expected after k ≈ √N. For an n-bit hash: √(2n) = 2n/2.
The lesson
A 128-bit hash (MD5) gives only 64 bits of security against collisions. So signatures need at least a 256-bit hash. That is why the slide says MD5 has "only 64-bit security".






7MAC: Message Authentication Code


Like a hash, with a key: MAC = CK(M). Gives integrity and also authenticity.
Why a key is needed (question from the slide)
A plain hash protects against random change, but a MITM can modify the message and simply compute a new hash. With a MAC, without K he cannot compute a valid tag for the modified message. Only someone holding K can produce it, so we also know it came from the sender.
In practice: HMAC = H((K ⊕ opad) ‖ H((K ⊕ ipad) ‖ M)). Not H(K ‖ M), because with MD5/SHA-1/SHA-256 that is vulnerable to length extension: you can append data to the message and compute a valid MAC without K (the Flickr API attack, 2009).






8Digital signatures


A handwritten signature ties a document to its signer, can be verified, is hard to forge, makes changing a signed document hard, and is legally binding. A digital signature gives the same: verifiable and unforgeable. Alice can prove to a third party that Bob (and only Bob, not even Alice) signed.
Signing the whole message with K− is slow and doubles the size. So we sign only the hash:
  1. Bob computes H(m) and signs it: s = KB−(H(m)).
  2. He sends m and s.
  3. Alice computes H(m) herself, and KB+(s).
  4. If the two are equal, the signature is valid.
If KB+(KB−(m)) = m, whoever signed used Bob's private key. Alice knows: Bob signed m, nobody else did, and Bob signed m and not m'. Non-repudiation: Alice can go to court with m and the signature.
Exploitation
A signature is worth exactly as much as the binding between the public key and Bob. If an attacker plants his own public key in Bob's name, "his" signatures verify. That is the problem the next sections solve. Also: a weak hash (MD5) lets a signature be moved to another document.
Real world
Code signing (Authenticode, iOS/Android updates), signed Git commits, DKIM in email (next chapter), biometric ID and smart cards, signed JWTs (RS256). SolarWinds (2020) showed that a valid signature does not help if the attacker is inside the build system.

10Key management: DH, MITM and KDC


Diffie-Hellman (seen in the symmetric chapter): both sides compute a shared secret, based on the difficulty of finding x from R = Gx mod N. Another example from the slides:
q = 11, α = 2
A: X_A = 4 → Y_A = 2⁴ mod 11 = 16 mod 11 = 5
B: X_B = 6 → Y_B = 2⁶ mod 11 = 64 mod 11 = 9
A: K = 9⁴ mod 11 = 6561 mod 11 = 5
B: K = 5⁶ mod 11 = 15625 mod 11 = 5 ✓
Key Distribution Center (KDC): a trusted server that shares a symmetric key with each user and hands out session keys. This is how Kerberos works (in Active Directory). Attacks: Golden Ticket (whoever steals the KDC key, krbtgt, issues tickets for any user), Kerberoasting.






11PKI, Certificate Authority and X.509


How do you know a public key really belongs to Bob? If it is digitally signed by someone whose public key we already have and trust (preferably signed recently). That builds a chain of trust.
PKI is a framework (not a specific technology) for publishing public keys, working across systems and vendors, providing authentication (certificates) and confidentiality. It requires trust in a third party.

Life cycle
1) Create a key pair. 2) Send a CSR (public key + identity). 3) The CA verifies identity. 4) The CA issues a signed certificate. A certificate expires and is renewed.
Revocation
Revoke a certificate if the private key leaked, the owner's status changed, or the CA's own key was compromised. Revocation list: CRL (today also OCSP).
Validation levels
DV: email or link to the domain owner (Let's Encrypt does this automatically with ACME). EV: legal and physical checks of the organization.
Trust models
Top-down: 100% trust in the root key, built into the software. Web of trust (PGP): the key is signed by many users, and trust accumulates.
When the chain breaks
DigiNotar (2011): a Dutch CA was breached and issued a fake certificate for *.google.com, used for MITM on ~300,000 users in Iran. The CA was removed from every browser and went bankrupt.
Superfish (Lenovo 2015): software that installed a root CA with the same private key on every machine to inject ads into HTTPS.
Organizations that do TLS inspection install their own root on every machine: legitimate MITM.
Extra defenses
Certificate Transparency: every certificate is logged publicly, and the domain owner sees certificates they did not request. CAA record in DNS: which CAs may issue for the domain. HSTS: the browser refuses HTTP.






12All together: TLS and SSH


TLS on the wire
Every TLS message travels inside a record with a 5-byte header, carried in TCP segments (port 443):
Byte(s)FieldValues
0Content type20 ChangeCipherSpec · 21 Alert · 22 Handshake · 23 Application data
1–2Version0x0303 = TLS 1.2 (TLS 1.3 also writes 0x0303 here for compatibility)
3–4Lengthlength of the payload, at most 214 bytes plus overhead
  1. ClientHello (type 22): client random (32 bytes), supported cipher suites, extensions: SNI (the hostname, in the clear), supported groups, key_share (the client's ECDHE public value in TLS 1.3).
  2. ServerHello: server random, the chosen cipher suite, the server's key share.
  3. Certificate: the server's X.509 chain. The client checks signatures up to a trusted root, the validity dates, and that the hostname matches SAN.
  4. CertificateVerify: the server signs the handshake transcript with its private key. This proves it owns the certificate and authenticates the DH values (prevents DH MITM).
  5. Finished (both sides): an HMAC over the whole transcript. If an attacker changed any message (e.g. removed strong ciphers), the Finished values do not match and the connection is aborted.
  6. Application data (type 23): encrypted with the session keys derived (HKDF) from the DH secret and both randoms, using AES-GCM or ChaCha20-Poly1305.
Record protocol (per the slide): takes data from the application, fragments it to a suitable size, (optionally) compresses it, computes an HMAC and encrypts according to what was agreed in the handshake, and passes it to the transport layer. Two-way authentication (mTLS): the client also sends a certificate (common between services).
SSH: the same principles, but no CA. On the first connection you receive the server's public key and store it in known_hosts (TOFU, trust on first use). If it changes: "WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED", i.e. maybe MITM.
Attacks on TLS (beyond the slides)
Heartbleed (2014, an OpenSSL memory leak including private keys), POODLE and BEAST (CBC), FREAK and Logjam (downgrade to export crypto), and SSL stripping (simply never letting the connection become HTTPS). TLS 1.3 removed all the old algorithms.
